# 企业级 RAG 离线流水线技术方案（含示例详解）

> 适用场景：企业内部知识库 / 客服问答 / 合规检索 / 多模态文档理解
> 设计原则：可观测、可回溯、可重放、容错降级、增量更新、质量门控

---

## 一、整体架构概览

离线流水线负责将原始文档转化为可检索的索引单元。企业级流水线采用 **DAG 有向无环图** 编排，每个节点独立可重试、可监控。

```
原始文档 → 文档接入 → 格式归一化 → 复杂度判定 → 解析路由 → 结构化提取
    → 数据清洗 → 语义分块 → 元数据增强 → 向量化 → 索引构建 → 质量校验 → 入库
```

**为什么要 DAG 而不是串行脚本？**

> **示例**：某公司每天新增 2000 份文档，其中 1800 份是简单的 Word 通知（1 秒处理完），200 份是扫描的合同（每份 30 秒）。如果用串行脚本，200 份合同会堵住整个队列，导致 1800 份通知要等 2 小时才能入库。DAG 架构下，简单文档走快速通道，复杂文档走慢速 worker 池，互不阻塞，通知 5 分钟内全部可检索。
>
> 此外，某个文档在"分块"阶段失败了，DAG 可以从分块阶段重跑，不需要重新解析（解析可能花了 30 秒）。串行脚本只能从头再来。

## 二、文档解析（Document Parsing）

### 2.1 为什么不能"一把梭"提取文本

**示例：同一份内容，不同格式，提取结果天差地别**

假设你有一份《员工报销管理制度》，分别存为三种格式：

| 格式 | 用 `pdftotext` 简单提取的结果 | 问题 |
|------|------|------|
| `.docx` | ✅ 文本完整，标题层级可从样式中读取 | 基本可用 |
| 文本型 PDF | ⚠️ 文本能提取，但"第三章 报销标准"和正文可能混在一行；表格变成一堆用空格分隔的数字 | 结构丢失 |
| 扫描型 PDF | ❌ 提取结果是空字符串或零星乱码 | 完全不可用 |

如果对所有格式都用同一种提取方式，扫描件直接报废，文本型 PDF 的表格变成"2024 500 800 1200 张三 李四 王五"这种无法理解的碎片。

**企业级做法**：按 MIME 类型（而非文件扩展名）路由到专用解析器。

> **为什么不能靠扩展名？** 示例：有人把 `合同.pdf` 重命名为 `合同.txt` 上传，按扩展名会走纯文本解析，结果读出来是 PDF 二进制乱码。用 `python-magic` 嗅探真实文件类型，能正确识别并路由到 PDF 解析器。

### 2.2 格式支持矩阵与选型理由

| 格式类别 | 具体格式 | 解析策略 | 为什么这么选 |
|---------|---------|---------|-------------|
| 原生文本 | TXT, MD, HTML | 编码检测 + 结构保留 | 本身就是结构化文本，直接用最快 |
| 办公文档 | DOCX, PPTX, XLSX | 解包 XML + 样式提取 | DOCX 本质是 ZIP 包，里面的 `document.xml` 带完整样式信息（标题级别、加粗、表格），比纯文本提取多了结构 |
| 文本型 PDF | 可选中文字的 PDF | 布局感知提取（pdfplumber/PyMuPDF） | PDF 没有"段落"概念，只有字符和坐标。需要根据坐标重建阅读顺序和表格 |
| 扫描型 PDF | 图片扫描件 | OCR + 版面分析 | 没有文本层，必须"看图识字" |
| 图片 | PNG, JPG | OCR + 视觉理解 | 同上 |
| 邮件 | EML, MSG | 正文 + 附件递归 | 邮件可能带 PDF/Excel 附件，需要拆出来单独走流水线 |
| 压缩包 | ZIP, RAR | 解压后递归 | 一个 ZIP 里可能有 50 份文档，必须逐个处理 |

**示例：邮件递归解析的价值**

> 销售发来一封邮件 `客户需求.eml`，正文写了几句需求，附件是 `需求清单.xlsx` 和 `技术方案.pdf`。如果只解析邮件正文，知识库只有那几句需求；递归解析后，附件里的完整需求清单和技术方案也全部入库。用户问"客户对延迟的要求是多少"，答案在 Excel 里，不递归就搜不到。

### 2.3 解析结果为什么要保留结构，而不是只存纯文本

**示例：一份技术手册的两种存储方式**

文档内容：
```
第二章 部署指南
2.1 环境要求
  操作系统：CentOS 7.6 及以上
  内存：最低 8GB，推荐 16GB
2.2 安装步骤
  步骤一：下载安装包
  步骤二：执行 install.sh
```

**只存纯文本**：
```
第二章 部署指南 2.1 环境要求 操作系统：CentOS 7.6 及以上 内存：最低 8GB...
```

**保留结构化元素**：
```
TitleElement(level=1, "第二章 部署指南")
TitleElement(level=2, "2.1 环境要求")
TextElement("操作系统：CentOS 7.6 及以上")
TextElement("内存：最低 8GB，推荐 16GB")
TitleElement(level=2, "2.2 安装步骤")
ListElement(["步骤一：下载安装包", "步骤二：执行 install.sh"])
```

**为什么结构很重要？**

1. **分块时不切断章节**：有了标题层级，可以在"2.1 环境要求"和"2.2 安装步骤"之间自然切分，不会把"内存最低8GB"和"步骤一下载安装包"塞进同一个块。
2. **检索结果可溯源**：用户问"内存要求"，返回结果时可以说"来自《部署指南》2.1 环境要求"，而不是"来自某段文本"。
3. **标题增强检索**：分块时可以把 `section_path`（"第二章 > 2.1 环境要求"）拼到块文本前面，检索"部署环境要求"时命中率大幅提升。

## 三、复杂文档解析与复杂度自主判断

### 3.1 为什么需要"复杂度判断"这一步

**反面示例：不做复杂度判断的后果**

> 某公司把所有文档都丢给同一个解析器（pdfplumber）。结果：
> - 1000 份简单的 Word 通知：处理正常，每份 1 秒
> - 50 份扫描的财务凭证：pdfplumber 提取出空白，全部变成空文档入库，用户搜任何内容都搜不到
> - 30 份多栏的行业研报：左右栏文字交错提取，变成"2024年营收增长15%市场份额持续提升行业前景广阔同比增长8%"这种左右栏混排的乱序文本
>
> 如果反过来，所有文档都走 OCR + 版面分析的重路径：
> - 1000 份简单通知本来 1 秒搞定，现在每份 30 秒，总耗时从 17 分钟变成 8 小时
> - 而且 OCR 对清晰的原生文本反而可能引入识别错误（如"0"识别成"O"）

**结论**：必须自动判断文档复杂度，简单文档走快车道，复杂文档走重路径，兼顾**质量**和**效率**。

---

### 3.2 复杂度自主判断——完整解决方案

#### 3.2.1 整体架构

复杂度判断引擎是一个独立的前置服务，在文档解析之前运行，输出复杂度等级和推荐解析路径。

```
文档输入
  │
  ├─→ [Step 1] 元数据快筛（<100ms，零成本）
  │     ├─ MIME 类型、文件大小、页数、加密状态
  │     └─ 输出：初步标签（simple / suspicious）
  │
  ├─→ [Step 2] 采样深度分析（<3s，按需采样）
  │     ├─ 采样策略：前3页 + 随机2页 + 末1页（共6页）
  │     ├─ 特征提取：8 维度特征向量
  │     └─ 输出：FeatureVector[8]
  │
  ├─→ [Step 3] 评分与分级
  │     ├─ 规则加权评分（默认）/ 轻量分类模型（可选）
  │     └─ 输出：ComplexityLevel(L0-L4) + 特征明细
  │
  └─→ [Step 4] 路由决策
        ├─ 按等级映射解析管道
        ├─ 特殊标记（需人工审核 / 需OCR / 需表格还原）
        └─ 输出：ParsePlan（解析计划）
```

#### 3.2.2 特征工程（8 维度详解）

每个特征归一化到 [0, 1]，具体计算方法：

| # | 特征名 | 计算方法 | 阈值参考 | 权重 |
|---|--------|---------|---------|------|
| F1 | 扫描可能性 | `1 - min(extractable_chars / (page_area * 0.003), 1.0)`；字符密度低于 50 字符/页判定为扫描页，取采样页中扫描页占比 | >0.5 高风险 | 0.25 |
| F2 | 版面复杂度 | 检测到的文本框数量归一化 + 列数检测（单列=0，双栏=0.5，三栏+=1.0）+ 浮动文本框数量 | >0.6 复杂 | 0.15 |
| F3 | 表格密度 | 每页平均表格数归一化 + 合并单元格比例 + 跨页表格数 | >0.4 密集 | 0.15 |
| F4 | 公式密度 | Unicode 数学符号（∑∫√π∂∞≠≤≥±×÷∈∉⊂⊃等）占比 + 独立公式行占比 | >0.02 公式密集 | 0.10 |
| F5 | 图像占比 | `sum(image_bbox_area) / total_page_area`，采样页平均 | >0.5 图为主 | 0.10 |
| F6 | 语言混合度 | fastText 检测采样文本语言，语言种类数归一化 + 语言切换频率 | >1 种混排 | 0.08 |
| F7 | 文档规模 | `min(pages / 100, 1.0)`，页数归一化 | >50页较大 | 0.07 |
| F8 | 非标准结构 | 检测修订痕迹（Word track changes）、批注、手写体痕迹、不规则列表 | 有则+0.5 | 0.10 |

**综合评分公式：**
```
ComplexityScore = Σ(Fi × Wi)，其中 ΣWi = 1.0
```

#### 3.2.3 分级标准与路由策略

| 等级 | 分数区间 | 典型特征 | 解析管道 | 单文档耗时 | 成本等级 |
|------|---------|---------|---------|-----------|---------|
| L0 极简 | [0, 0.1) | 纯文本/Markdown，<10页 | 直接文本提取 + 编码检测 | <1s | 极低 |
| L1 标准 | [0.1, 0.3) | 普通PDF/Word，单栏，无复杂表格 | 布局感知解析（pdfplumber/unstructured） | 2-5s | 低 |
| L2 复杂 | [0.3, 0.55) | 多栏 / 含表格 / 图文混排 / 50页+ | 版面分析（DocLayout-YOLO）+ 表格识别（PP-Structure） | 5-20s | 中 |
| L3 高复杂 | [0.55, 0.8) | 扫描件 / 密集表格 / 公式 / 跨页元素 | OCR（PaddleOCR）+ 版面分析 + 表格还原 + 公式识别 | 20-60s | 高 |
| L4 极复杂 | [0.8, 1.0] | 手写体 / 多语言混排 / 非结构化聊天 / 严重低质 | 多模态大模型逐页理解 + 人工审核队列 | 60s+ / 人工 | 极高 |

**路由伪逻辑：**
```
if F1(扫描可能性) > 0.6:
    强制至少 L3（扫描件必须走OCR）
if F3(表格密度) > 0.5 and F1 < 0.6:
    至少 L2（需要表格结构还原）
if F4(公式密度) > 0.05:
    标记 formula_enhanced=true（追加公式识别步骤）
if F6(语言混合度) > 1.5:
    标记 multilingual=true（使用多语言OCR和嵌入模型）
if 文档加密 or 损坏:
    直接进入 DLQ，不进入解析管道
```

#### 3.2.4 采样策略详解

**为什么采样而不是全量分析？** 全量分析 156 页文档要 30 秒，采样 6 页只需要 2 秒，且对"前轻后重"型文档有足够的覆盖率。

**采样规则：**
- 固定采样：第 1 页（封面/目录）、第 2-3 页（正文开头）、最后 1 页（附录/签章）
- 随机采样：在剩余页面中均匀随机取 2 页
- 自适应追加：如果随机采样页的特征方差大（如一页文本、一页扫描），再追加 2 页随机采样，最多 8 页
- 小文档（≤10 页）：全量分析，不采样

#### 3.2.5 反馈闭环与模型调优

复杂度判断不是一成不变的，需要持续优化：

```
人工修正入口
  │
  ├─→ 运营在审核界面标记："此文档应为L3而非L1"
  ├─→ 记录：doc_id, 原等级, 修正等级, 特征向量
  ├─→ 积累 100+ 条修正样本后：
  │     ├─ 方案A：重新拟合规则权重（线性回归）
  │     └─ 方案B：训练轻量分类模型（逻辑回归 / 随机森林，特征即上述8维）
  └─→ A/B 验证：新模型在标注集上准确率提升 > 5% 才上线
```

**企业级实现建议**：前期用规则加权（可解释、易调试），积累 500+ 标注样本后切换为轻量模型，规则作为兜底和可解释性参考。

### 3.3 复杂文档专项解析——完整解决方案

#### 3.3.1 扫描件 / 图片型 PDF 解决方案

**端到端处理流水线：**

```
原始扫描页
  │
  ├─→ [1] 图像预处理
  │     ├─ 格式统一：转 PNG，300 DPI
  │     ├─ 去歪斜：Hough 变换检测文字行角度 → 旋转校正（精度 ±0.5°）
  │     ├─ 去噪：非局部均值去噪（NLMD），保留文字边缘
  │     ├─ 增强：自适应二值化（Sauvola，窗口 25×25，k=0.2）
  │     └─ 裁剪：去除扫描黑边
  │
  ├─→ [2] 版面分析（Layout Analysis）
  │     ├─ 模型：DocLayout-YOLO / PP-StructureV2
  │     ├─ 输出区域类型：title / text / table / figure / formula / header / footer
  │     └─ 每个区域：bbox 坐标 + 类别 + 置信度
  │
  ├─→ [3] 区域级识别
  │     ├─ text/title 区域 → PaddleOCR 识别文字 + 排序
  │     ├─ table 区域 → 表格结构识别（SLANet/TableMaster）→ HTML
  │     ├─ formula 区域 → UniMERNet → LaTeX
  │     ├─ figure 区域 → 可选 VLM 生成图片描述（"图3：系统架构图，包含前端、API网关、微服务层..."）
  │     └─ header/footer → 标记，后续清洗阶段移除
  │
  ├─→ [4] 阅读顺序重建
  │     ├─ 单栏：从上到下、从左到右
  │     ├─ 多栏：先按 x 坐标聚类分列，列内从上到下
  │     └─ 浮动框：侧边栏/注释框标记为独立元素，不混入主阅读流
  │
  └─→ [5] 后处理与校验
        ├─ OCR 置信度统计：低置信度字符（<0.7）标记并记录
        ├─ 乱码检测：异常字符占比 > 5% → 标记低质量
        └─ 输出：结构化元素列表 + 每页 OCR 质量分
```

**工具链选型：**

| 环节 | 开源方案 | 商用方案 | 选型建议 |
|------|---------|---------|---------|
| 预处理 | OpenCV + deskew | — | OpenCV 足够 |
| 版面分析 | DocLayout-YOLO, PP-StructureV2 | Azure Document Intelligence | 中文场景 PP-StructureV2 开箱即用 |
| OCR | PaddleOCR, RapidOCR | 百度OCR, 腾讯OCR, Azure OCR | 私有化用 PaddleOCR，云端用商用API |
| 表格识别 | PP-Structure SLANet, TableMaster | Azure Form Recognizer | 表格密集场景 Azure 准确率更高 |
| 公式识别 | UniMERNet, LaTeX-OCR, Pix2Tex | Mathpix | 学术文档多的场景考虑 Mathpix |
| 一站式 | MinerU, marker | — | MinerU 对中文 PDF 支持好，推荐首选 |

**质量指标：**
- OCR 字符错误率（CER）：目标 < 2%（清晰扫描件），< 5%（低质扫描件可接受）
- 版面区域检测 mAP：目标 > 0.85
- 端到端文本提取准确率（与人工标注比对）：目标 > 95%

**示例：倾斜扫描合同的处理效果**

> 原始扫描件倾斜 5° + 噪点 + 光照不均。直接 OCR 把"有限公司"识别为"有阳公司""公同"。经过去歪斜 + 去噪 + 二值化预处理后，OCR 准确率从 92% 提升到 99%。对专有名词（公司名、人名）的召回率从 78% 提升到 96%。

#### 3.3.2 复杂表格解决方案

**表格处理的完整流程：**

```
检测到表格区域
  │
  ├─→ [1] 表格分类
  │     ├─ 有框线表格：线条清晰，单元格边界明确
  │     ├─ 无框线表格：靠文本对齐推断列（如财务报表、名单）
  │     └─ 半框线表格：只有横线或只有竖线
  │
  ├─→ [2] 结构还原
  │     ├─ 有框线：检测横线竖线 → 求交 → 生成单元格网格 → 合并单元格识别（跨线检测）
  │     ├─ 无框线：文本行投影 → 列坐标聚类 → DBSCAN 聚类列边界 → 推断单元格
  │     └─ 输出：二维数组 cells[row][col]，每个 cell 含 text, rowspan, colspan
  │
  ├─→ [3] 跨页表格合并
  │     ├─ 检测相邻页表格：列数一致 + 列宽偏差 < 10% + 位置对齐
  │     ├─ 合并为一个逻辑表格，记录 page_span=[12,13]
  │     └─ 表头传播：仅首页有表头时，将表头复制到每个逻辑子表
  │
  ├─→ [4] 表头识别与层级
  │     ├─ 单行表头：直接提取
  │     ├─ 多级表头："2024年"下分"Q1 Q2 Q3 Q4" → 展开为完整列名"2024年-Q1"
  │     └─ 表头校验：表头单元格通常有背景色/加粗/居中，用样式特征辅助判断
  │
  └─→ [5] 多格式表示（三存策略）
        ├─ Markdown 表格：用于向量检索和 LLM 阅读（主表示）
        ├─ HTML 表格：保留完整结构（rowspan/colspan），用于精确渲染
        └─ 逐行扁平化：每行转为 "列名1: 值1 | 列名2: 值2"，提高关键词召回
```

**表格分块策略（与第五章联动）：**

```
大表格（>30行）分块算法：
1. 提取表头 headers
2. 按行组切分，每组 target_rows = 15 行（可配置）
3. 每个块文本 = headers_markdown + rows_group_markdown
4. 块元数据标记 chunk_type="table"，table_id, row_range=[1,15]
5. 可选：生成表格摘要 "该表展示了XX，包含字段：A, B, C..."，作为独立块提高召回
```

**常见坑与解决方案：**

| 问题 | 表现 | 解决方案 |
|------|------|---------|
| 合并单元格丢失 | "总计"行跨3列，还原后变成3个重复"总计" | 检测跨行跨列，合并单元格只在左上角存值 |
| 数字列对齐错乱 | 1,234.56 被拆成 "1," "234" ".56" | 关闭OCR的自动分列，按表格结构模型输出 |
| 表格内换行 | 单元格内文字换行，被误判为新行 | 同一单元格内的多行文本合并，用空格连接 |
| 旋转表格 | 横向表格（landscape） | 检测页面方向，自动旋转 90° 后再识别 |

**示例：跨页财务报表的处理**

> 80 行报表在第 12-13 间断开，第 13 页无表头。系统检测到两页表格列数（4列）和列宽一致，自动合并。合并后分块：块1=`[表头]+营业收入/营业成本`，块2=`[表头]+毛利润/净利润`。用户搜"2024年毛利润"时，"2024年"和"毛利润"在同一块，精确命中。如果不合并，第13页的"毛利润 400万 500万 650万"因无表头语义不明，检索匹配度低。

#### 3.3.3 多栏排版 / 图文混排解决方案

**核心问题**：PDF 只有字符和坐标，没有"栏"的概念。逐行提取会把左右栏交错拼接。

**解决方案：基于版面分析的列重建**

```
页面图像 / PDF 坐标
  │
  ├─→ [1] 区域检测（DocLayout-YOLO）
  │     └─ 输出所有文本块的 bbox + 类别
  │
  ├─→ [2] 列聚类
  │     ├─ 按文本块的 x_center 做一维聚类（DBSCAN，eps=页面宽度的 1/4）
  │     ├─ 聚类数 = 栏数
  │     └─ 每栏内的文本块按 y_top 排序
  │
  ├─→ [3] 阅读顺序确定
  │     ├─ 默认：从左到右逐栏阅读（左栏读完 → 右栏）
  │     ├─ 跨栏元素：通栏标题/图表标记为 spanning，在所有栏之前/之后
  │     └─ 浮动框：侧边注释框标记为 aside，独立于主阅读流
  │
  ├─→ [4] 栏内段落重建
  │     ├─ 相邻文本块纵向间距 < 行高 ×1.5 → 同一段落
  │     ├─ 行末无标点 + 下一行首行不缩进 → 跨行合并（修复断行）
  │     └─ 首行缩进 + 间距大 → 新段落
  │
  └─→ [5] 图文关联
        ├─ 图片下方/上方的文本检测为 caption（"图1：..." / "表2：..."）
        ├─ caption 与图片绑定存储
        └─ 图片可选 VLM 生成描述，与 caption 合并
```

**栏数检测的兜底方法**（不依赖深度学习模型）：
- 对页面做水平投影，统计每行的字符 x 坐标分布
- 如果 x 坐标出现明显的"双峰"或"多峰"（峰之间有空白间隔 > 50px），判定为多栏
- 峰的数量 = 栏数

**示例：两栏研报的提取对比**

> 逐行提取结果："2024年，新能源汽车 与此同时，充电基础设施 市场持续增长，全年 建设也在加速..."（左右栏交错）
>
> 版面分析 + 列聚类后：左栏文本完整 → 右栏文本完整，语义连贯性从 ~50% 提升到 98%，检索召回率提升 25%。

#### 3.3.4 公式解决方案

**处理流程：**

```
公式检测
  │
  ├─→ 行内公式：$...$ 标记 / 数学符号密集的短文本
  └─ 块级公式：独立成行、居中、符号密度高
  │
  ├─→ 公式识别（图片型公式）
  │     └─ UniMERNet / LaTeX-OCR → LaTeX 字符串
  │
  └─→ 存储与检索优化
        ├─ 原文保留 LaTeX（用于展示和精确引用）
        ├─ 检索辅助：可选将 LaTeX 转为自然语言描述
        │   例："E=mc²" → "能量等于质量乘以光速的平方"
        └─ 块级公式保留前后各 1-2 句上下文（公式通常需要上下文理解）
```

**工具**：UniMERNet（中文场景好）、LaTeX-OCR（pix2tex，英文场景）、Mathpix（商用，准确率最高）。

#### 3.3.5 长文档（>100 页）解决方案

**挑战**：解析耗时长、内存占用大、全局结构（目录/交叉引用）维护困难。

**解决方案：分页并行 + 全局结构重建**

```
长文档输入
  │
  ├─→ [1] 拆分为页级任务
  │     ├─ PDF 按页拆分（PyMuPDF 提取单页）
  │     └─ 每页作为独立任务送入 worker 池（并行解析）
  │
  ├─→ [2] 全局结构提取
  │     ├─ 目录页解析：提取 TOC（章节标题 + 页码）
  │     ├─ 标题层级推断：从字体大小/加粗/编号模式推断 heading level
  │     └─ 构建全局标题树：Chapter > Section > Subsection
  │
  ├─→ [3] 页级解析结果合并
  │     ├─ 按页码排序所有元素
  │     ├─ 用全局标题树为每个元素标注 section_path
  │     └─ 跨页元素合并（表格、段落、列表）
  │
  ├─→ [4] 交叉引用解析（可选）
  │     ├─ 正则匹配"见第X章"/"参见表Y"/"如图Z所示"
  │     ├─ 解析为内部锚点链接（不改变文本，但记录引用关系）
  │     └─ 可用于知识图谱构建
  │
  └─→ [5] 内存优化
        ├─ 页级解析结果写入临时文件（JSONL），不全量驻留内存
        ├─ 合并阶段流式读取，逐页输出最终元素
        └─ 单文档内存峰值控制在 500MB 以内
```

**并行度控制**：CPU 密集型解析（OCR/版面分析）按 CPU 核数设 worker 数；IO 密集型（文本提取）可设 2-3 倍核数。

#### 3.3.6 多语言混排解决方案

**场景**：中英混排技术文档、日资企业的中日文合同、跨国公司的多语言手册。

**处理要点：**

1. **语言检测粒度**：不只是文档级，要做到**段落级/行级**语言检测。一个文档可能中文段落里夹杂英文术语。
2. **OCR 模型选择**：
   - 中英混排：PaddleOCR 的中文模型（内置英文支持）
   - 中日韩混排：使用支持 CJK 的多语言模型
   - 含 RTL 语言（阿拉伯语/希伯来语）：需特殊处理文本方向
3. **嵌入模型**：使用多语言嵌入模型（bge-m3, E5-mistral, multilingual-e5-large），不要用单语言模型处理混排文档。
4. **分词**：BM25 索引时，不同语言段落使用对应分词器（中文用 IK/Jieba，英文用标准分词）。

### 3.4 解析质量保障体系

#### 3.4.1 解析结果自动校验

每个文档解析完成后，自动运行质量校验：

| 校验项 | 方法 | 不通过的处理 |
|--------|------|-------------|
| 文本非空 | 提取总字符数 > 0 | 扫描件走 OCR 重试；仍为空 → DLQ |
| 乱码率 | � + 异常字符占比 < 3% | 标记低质量，进入人工审核 |
| OCR 置信度 | 平均置信度 > 0.8（扫描件） | 低置信度页标记，建议人工复核 |
| 结构完整性 | 标题树无孤立节点、表格行列数一致 | 记录警告，不阻断 |
| 元素覆盖率 | 页面内容被元素覆盖 > 80% | 可能有遗漏区域，追加一次全页 OCR |
| 语言一致性 | 文档主语言占比 > 70% | 标记多语言，使用多语言模型 |

#### 3.4.2 置信度评分体系

为每个文档输出解析质量分（0-100），随元数据存储：

```
ParseQualityScore = 0.3 × 文本完整性
                  + 0.25 × OCR平均置信度（扫描件）/ 布局解析置信度（文本PDF）
                  + 0.2 × 结构完整度
                  + 0.15 × 乱码率反向
                  + 0.1 × 表格还原准确率（有表格时）
```

- ≥ 90：高质量，直接进入下一阶段
- 70-89：中质量，正常处理但标记
- 50-69：低质量，进入人工审核队列
- < 50：解析失败，DLQ + 告警

#### 3.4.3 人工审核工作流

```
低质量文档进入审核队列
  │
  ├─→ 审核界面展示：原文截图 + 解析结果对比 + 质量分明细
  ├─→ 审核员操作：
  │     ├─ 通过：确认解析结果可用
  │     ├─ 修正：手动编辑解析结果（如修正OCR错误、调整表格）
  │     ├─ 重解析：选择其他解析管道重试（如换OCR模型）
  │     └─ 拒绝：文档无法解析，通知上传者
  └─→ 修正结果回流：
        ├─ 作为标注样本用于模型调优
        └─ 记录复杂度等级修正（反馈闭环）
```

#### 3.4.4 解析器 A/B 测试

当引入新的解析工具或模型升级时，不直接全量替换：

1. 选取 500 份代表性文档（覆盖各复杂度等级）
2. 新旧解析器并行处理
3. 对比指标：文本准确率、表格还原率、处理耗时、资源消耗
4. 新解析器在核心指标上优于旧版 + 无严重回归 → 灰度 10% → 50% → 100%
5. 灰度期间保留旧解析器作为降级兜底

## 四、数据清洗（Data Cleaning）

### 4.1 为什么清洗是"必须"而不是"可选"

**示例：未清洗的文档对检索的破坏**

某公司的制度 PDF 每页底部都有页眉页脚：
```
【页眉】XX科技有限公司 内部机密 文件编号：ZD-2024-001
【页脚】第 X 页 / 共 50 页 版权所有 违者必究
```

50 页的文档，"XX科技有限公司 内部机密"这句话出现了 50 次。如果不清洗：

1. **BM25 检索被污染**：用户搜"内部机密"，这份文档的 BM25 分数极高（因为关键词重复 50 次），但用户真正想找的可能是另一份标注为机密的项目文档。
2. **向量嵌入偏移**：每个块都带着"XX科技有限公司内部机密第X页"，嵌入向量被这些无意义信息"拉偏"，块与块之间的语义区分度下降。
3. **LLM 回答被干扰**：检索返回的 5 个块都带着页眉页脚，LLM 的上下文里充斥着"内部机密""版权所有"，浪费 token 且可能干扰回答。

**清洗后**：页眉页脚被识别并移除，每个块只保留真正的正文内容。

### 4.2 各清洗环节的具体示例

#### 4.2.1 页眉页脚检测

**怎么自动识别？** 不是写死"底部的就是页脚"，而是用**跨页重复度**：

> 示例：对 50 页文档，取每页顶部 3 行和底部 3 行，归一化后统计出现频率。"XX科技有限公司 内部机密"在 50 页中出现了 48 页（96%），判定为页眉。"第 X 页 / 共 50 页"虽然页码数字不同，但"第 页 共 页"的模式匹配度 > 90%，判定为页脚。

**为什么不能简单删除底部文字？** 有些文档的最后一页底部是"审批人：张三 2024年1月1日"这样的重要签名信息，它只出现一次，不会被误判为页脚。跨页重复度检测能区分"每页都有的噪声"和"只出现一次的重要内容"。

#### 4.2.2 乱码检测与降级

**示例**：一份 GBK 编码的文件被错误地用 UTF-8 打开，提取出大量 `�`（Unicode 替换符）和乱码字符：
```
æ–‡ä»¶ç®¡ç†åˆ¶åº¦è§„å®šï¼Œå'˜å·¥å¿…é »é ™å®ˆ
```

如果不检测直接入库，用户搜任何内容都匹配不到（因为全是乱码），而且乱码文本的嵌入向量是随机噪声，可能在向量空间中"意外匹配"到不相关的查询。

**企业级做法**：检测到 `�` 占比 > 3% 时，不入库，进入死信队列（DLQ），告警运营人员重新处理（尝试其他编码）。这比"凑合入库"好得多——一个空结果比一个错误结果更安全。

#### 4.2.3 语义去重：MinHash + LSH

**示例：三个版本的同一份制度文件**

知识库中有：
- `报销制度_v1.pdf`（2023年版，3000字）
- `报销制度_v2.pdf`（2024年修订版，3100字，修改了第3章的报销限额）
- `报销制度_最终版.pdf`（某人把 v2 另存为"最终版"，内容和 v2 完全一样）

**不做去重的后果**：用户搜"报销限额是多少"，检索返回 3 个结果，其中 v2 和"最终版"内容完全一样，v1 是旧版本。LLM 可能看到 v1 的旧限额（500元）和 v2 的新限额（800元），回答时产生矛盾，或者引用了已作废的 v1。

**近似去重的处理**：
1. 精确去重：v2 和"最终版"内容 hash 完全一致，只保留一份，记录"别名：报销制度_最终版"
2. 近似去重：v1 和 v2 的 MinHash Jaccard 相似度 = 0.87（超过阈值 0.85），判定为近似重复
3. 策略：保留最新版本 v2，v1 标记为 `superseded_by=v2`，检索时默认不返回旧版本，但保留可追溯（合规场景可能需要查历史版本）

#### 4.2.4 质量过滤：什么内容该被拦下来

**示例：一份"碎片文档"**

某系统自动导出的日志片段，清洗后仍然是：
```
[2024-01-15 10:23:01] INFO
[2024-01-15 10:23:02] WARN connection timeout
[2024-01-15 10:23:03] ERROR
```

质量检测：
- 平均块长度：15 字符（远低于阈值 100）
- 完整句子比：0%（没有句号结尾的句子）
- 信息密度：大量时间戳和日志级别，有效信息极少

**处理**：质量分 < 阈值，不进入主索引，进入"低质量区"。用户检索时默认不返回，但可以通过专门的日志检索接口查询。

> **为什么不直接删除？** 日志可能在排障场景下有用。但放在主索引里会污染通用问答的结果。分区存储 + 按需检索是平衡方案。

## 五、分块策略（Chunking Strategy）

### 5.1 为什么分块是 RAG 质量的"胜负手"

**示例：固定长度分块如何毁掉一个问答**

文档原文（《劳动合同法》相关条款）：
```
第三十九条 劳动者有下列情形之一的，用人单位可以解除劳动合同：
（一）在试用期间被证明不符合录用条件的；
（二）严重违反用人单位的规章制度的；
（三）严重失职，营私舞弊，给用人单位造成重大损害的；
（四）劳动者同时与其他用人单位建立劳动关系，对完成本单位的工作任务造成严重影响...
```

**固定 100 字符分块（不考虑语义边界）**：

块 A：
```
第三十九条 劳动者有下列情形之一的，用人单位可以解除劳动合同：（一）在试用期间被证明不符合录用条件的；（二）严重违反用人单位的规章
```

块 B：
```
制度的；（三）严重失职，营私舞弊，给用人单位造成重大损害的；（四）劳动者同时与其他用人单位建立劳动关系...
```

**问题**：
- 块 A 结尾是"规章"，块 B 开头是"制度的"——"规章制度"这个词被硬生生切断
- 块 B 单独看不知道在说什么（没有"用人单位可以解除劳动合同"这个前提）
- 用户问"严重违反规章制度能解除合同吗"，块 A 有"解除劳动合同"和"严重违反"但没说完，块 B 有"制度的"但没有前提，两个块的向量匹配度都不高，可能都搜不到

**语义分块（在句子/条款边界切分）**：

块 A：
```
第三十九条 劳动者有下列情形之一的，用人单位可以解除劳动合同：
（一）在试用期间被证明不符合录用条件的；
（二）严重违反用人单位的规章制度的；
```

块 B：
```
（三）严重失职，营私舞弊，给用人单位造成重大损害的；
（四）劳动者同时与其他用人单位建立劳动关系，对完成本单位的工作任务造成严重影响...
```

每个块都是完整的语义单元，用户问什么都能精确匹配。

### 5.2 父子分块：为什么"检索小块、返回大块"效果最好

**示例：客服知识库中的一个长段落**

文档中有一段关于"退货政策"的内容（约 1200 token）：
```
7.1 退货政策
7.1.1 退货条件
商品签收后7天内，在不影响二次销售的情况下，消费者可以申请无理由退货。
以下商品不支持7天无理由退货：（1）定制类商品；（2）鲜活易腐商品；（3）在线下载或拆封的音像制品、计算机软件等数字化商品；（4）交付的报纸、期刊。
7.1.2 退货流程
第一步：在订单详情页点击"申请退货"
第二步：选择退货原因，上传商品照片
第三步：等待商家审核（24小时内）
第四步：审核通过后寄回商品，填写物流单号
第五步：商家收到商品并确认无误后，48小时内退款
7.1.3 运费承担
因商品质量问题退货，运费由商家承担；因个人原因退货，运费由消费者承担。
...
```

**方案 A：整块作为一个 chunk（1200 token）**
- 检索"退货审核要多久"：能匹配到，但整个 1200 token 都返回给 LLM，其中大部分内容（退货条件、运费承担）与问题无关，浪费上下文且可能干扰回答
- 检索"定制商品能退货吗"：匹配到，但答案淹没在 1200 token 中，LLM 可能忽略

**方案 B：切成 3 个小块（每块 400 token），检索到哪个返回哪个**
- 检索"退货审核要多久"：匹配到"7.1.2 退货流程"块，返回 400 token ✅
- 但检索"退货运费谁出"：匹配到"7.1.3 运费承担"块，这个块只有 2 句话，缺少"退货政策"的大前提（如"7天内"），LLM 回答时可能遗漏前提条件

**方案 C：父子分块（推荐）**
- 父块：整个"7.1 退货政策"（1200 token），用于喂给 LLM
- 子块：7.1.1、7.1.2、7.1.3 各一个（约 400 token），用于向量检索
- 检索"退货审核要多久" → 命中子块 7.1.2 → 返回对应的父块（完整的退货政策）

这样既保证了**检索精度**（小块更容易精确匹配），又保证了**上下文完整**（父块包含完整的前提和相关条款）。

### 5.3 表格分块的具体示例

**示例：一份 100 行的员工信息表**

| 工号 | 姓名 | 部门 | 职位 | 入职日期 | 薪资 |
|------|------|------|------|----------|------|
| E001 | 张三 | 技术部 | 工程师 | 2020-03-15 | 25000 |
| E002 | 李四 | 市场部 | 经理 | 2019-07-20 | 30000 |
| ...（共 100 行） |

**错误做法 1：整个表作为一个块**
- 块大小可能达到 3000+ token，超过嵌入模型最优区间
- 用户问"张三的薪资是多少"，返回整个表，LLM 要在 100 行里找张三，浪费 token 且可能找错

**错误做法 2：每行一个块，不带表头**
- 块内容：`E001 张三 技术部 工程师 2020-03-15 25000`
- 没有表头，"25000"不知道是薪资还是工号，向量检索"薪资"时匹配不到

**正确做法：表头 + N 行一组**
- 块 1：`[表头] + 第1-20行`
- 块 2：`[表头] + 第21-40行`
- ...
- 每个块都带表头，"25000"在"薪资"列的上下文中，语义清晰

### 5.4 分块参数为什么要按场景调

**示例：同样是 512 token，不同场景效果不同**

| 场景 | 块太大的问题 | 块太小的问题 | 推荐大小 |
|------|------------|------------|---------|
| 客服问答 | 用户问"怎么退货"，返回的块里混着换货、维修的内容，LLM 回答跑偏 | 块只有"点击申请按钮"，缺少前置条件，回答不完整 | 384 token |
| 法律合规 | 一个条款被切断，"应当"和"不得"分在两个块，语义矛盾 | 引用法条时缺少条款编号，无法溯源 | 1024 token |
| 技术文档 | API 文档里一个接口的请求和响应分在不同块 | 代码示例被切断，无法复制使用 | 768 token |

> **关键认知**：不存在"最优分块大小"。必须根据你的文档类型和查询场景做 A/B 测试，用标注的问答对评测 Recall@K 和端到端回答准确率来确定。

## 六、索引策略（Indexing Strategy）

### 6.1 为什么纯向量检索不够，必须混合检索

**示例：向量检索的"盲区"**

用户查询：`"错误代码 0x80070005 怎么解决"`

- **向量检索**：嵌入模型可能把"0x80070005"当成无意义的符号串（很多嵌入模型对长数字/十六进制编码能力弱），匹配到"Windows 错误排查指南"这种泛化文档，而不是精确描述这个错误码的那篇 KB 文章
- **BM25 检索**：`0x80070005` 是精确字符串，倒排索引直接命中包含这个错误码的文档，精准度 100%

另一个方向，用户查询：`"电脑老是蓝屏怎么办"`

- **BM25**：可能只匹配到包含"蓝屏"的文档，但如果某篇文章写的是"系统崩溃、死机排查"（没有"蓝屏"这个词），BM25 搜不到
- **向量检索**：能理解"蓝屏"和"系统崩溃、死机"语义相近，能召回这篇文章

**混合检索 = 向量的语义理解 + BM25 的精确匹配**，两者互补。

> **实际数据**：在企业知识库场景中，纯向量检索的 Recall@10 通常在 75-85%，加入 BM25 混合后能提升到 90-95%。对于包含大量专有名词、产品编号、错误码的技术文档，提升更明显。

### 6.2 向量索引算法选择示例

**HNSW vs 暴力搜索的实际差异**

假设你有 100 万个向量（1024 维），查询一次：

| 算法 | 召回率 | 查询延迟 | 内存占用 |
|------|--------|---------|---------|
| 暴力搜索（Flat） | 100% | ~50ms（CPU）/ ~10ms（GPU） | ~4GB（全量向量） |
| HNSW（M=16, ef=128） | ~97% | ~2ms | ~5GB（向量 + 图结构） |

- 100 万向量时，暴力搜索还能接受（50ms），但如果是 5000 万向量，暴力搜索一次要 2-3 秒，用户无法接受
- HNSW 通过构建图索引，把搜索复杂度从 O(N) 降到 O(log N)，5000 万向量也能在 5ms 内返回
- 代价是 3% 的召回率损失，以及更多的内存和构建时间

**企业级选择**：1000 万以内用 HNSW（召回和延迟的最佳平衡），超过 1 亿考虑 DiskANN（SSD 存储，延迟稍高但成本低得多）。

### 6.3 元数据过滤：权限隔离的具体示例

**示例：没有权限过滤的安全事故**

某公司知识库中有：
- 全员可见的《员工手册》
- 财务部可见的《薪酬管理制度》（含各岗位薪资范围）
- 高管可见的《并购方案》

如果检索时不做权限过滤：
- 普通员工搜"薪资"，向量检索可能返回《薪酬管理制度》中的块，员工看到了管理层薪资范围 → **数据泄露**
- 更严重的是，普通员工搜"公司战略"，可能返回《并购方案》的内容 → **重大合规事故**

**企业级做法：预过滤**

每个块携带 `access_level` 和 `authorized_departments` 元数据。检索时：
1. 先从用户身份获取其权限（如 `department=技术部, level=普通员工`）
2. 在向量搜索前加过滤条件：`access_level <= "内部公开" AND "技术部" IN authorized_departments`
3. 只在有权限的候选集中做向量相似度计算

这样普通员工的检索结果里根本不会出现薪酬和并购文档，从物理上杜绝泄露。

> **为什么用预过滤而不是后过滤？** 后过滤是先搜全库再剔除无权限的，但如果 Top 10 结果里有 8 个是无权限的，过滤后只剩 2 个结果，用户看到的答案不完整。预过滤在搜索前就限定了候选范围，保证返回的都是有权限的且数量充足。

### 6.4 增量更新：为什么不能每次全量重建

**示例：全量重建的痛点**

某公司知识库有 50 万份文档，全量重建索引需要：
- 重新解析所有文档：约 8 小时
- 重新生成所有向量（500 万块）：约 4 小时（用 GPU）
- 重建 HNSW 索引：约 2 小时
- **总计：14 小时**

如果每天有 100 份文档新增/修改，每次都全量重建：
- 每天有 14 小时索引在重建中，期间新文档不可检索
- 嵌入模型的 API 调用费用每天多花几千元（重复计算不变的文档）
- 重建期间如果出问题，整个知识库不可用

**增量更新的做法**：
1. 文档入库时计算内容 hash（如对归一化后的文本算 SHA256）
2. 新增文档时，hash 不存在 → 走完整流水线
3. 修改文档时，hash 变化 → 只删除该文档的旧块，插入新块（秒级完成）
4. 未变化的文档 → 跳过

100 份变更文档的增量处理只需要 10-20 分钟，且不影响已有文档的检索服务。

### 6.5 中文 BM25 的自定义词典示例

**示例：没有自定义词典时的分词灾难**

企业内部术语：`"RAGFlow"`、`"LangGraph"`、`"飞书多维表格"`、`"光前村健身房"`

**默认 IK 分词器的分词结果**：
- `RAGFlow` → `R`, `A`, `G`, `F`, `l`, `o`, `w`（被拆成单个字母！）
- `LangGraph` → `L`, `a`, `n`, `g`, `G`, `r`, `a`, `p`, `h`
- `飞书多维表格` → `飞`, `书`, `多`, `维`, `表`, `格`（被拆成单字）

分词被拆碎后，BM25 检索"RAGFlow"时，匹配的是所有包含字母 R/A/G/F 的文档，完全失去精确匹配能力。

**加入自定义词典后**：
- `RAGFlow` → `RAGFlow`（作为一个整体词）
- `LangGraph` → `LangGraph`
- `飞书多维表格` → `飞书`, `多维表格`

BM25 检索"RAGFlow"时，精确命中包含这个产品名的文档。

> **企业级维护**：自定义词典不是一次性的，需要持续更新。建议建立"新词发现"机制——统计索引中未被识别为完整词的高频字符串，人工审核后加入词典。例如新上线的产品名"豆包专业版"，刚出现时会被拆成"豆", "包", "专", "业", "版"，发现后加入词典。

## 七、质量保障与可观测性

### 7.1 为什么需要离线评测

**示例："感觉检索还行"是怎么出问题的**

某团队上线 RAG 后，测试人员随便搜了几个问题，觉得"还可以"就上线了。运行一个月后用户反馈：
- 搜"年假多少天"返回的是 2023 年的旧制度（5 天），实际 2024 年已改为 10 天
- 搜"加班费计算"返回的是其他部门的制度，不适用本部门
- 有 15% 的问题返回"未找到相关内容"，但其实答案就在知识库中

没有量化评测，这些问题发现不了。**企业级做法**：构建 200-500 条标注问答对（问题 + 标准答案所在的文档/块），每次流水线变更后跑一遍，看 Recall@5、MRR 等指标是否下降。

### 7.2 死信队列（DLQ）的价值

**示例：一个失败文档不应该拖垮整个流水线**

某天有 500 份文档待处理，其中 1 份是损坏的 PDF（文件不完整），解析时抛出异常。

- **没有 DLQ**：串行处理到这份文档时崩溃，后面 300 份文档全部卡住，直到人工介入
- **有 DLQ**：这份文档失败 3 次后进入 DLQ，记录错误信息，流水线继续处理剩下的 499 份。运维人员事后查看 DLQ，发现是文件损坏，通知上传者重新提交

DLQ 保证了**部分失败不影响整体**，这是企业级系统和 demo 的核心区别之一。
