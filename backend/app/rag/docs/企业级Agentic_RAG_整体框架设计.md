# 企业级 Agentic RAG 整体框架设计

> 定位：面向企业内部知识问答/检索场景的 Agentic RAG 完整架构蓝本。
> 目标：把"能跑的通"升级为"可治理、可观测、可评测、可审计、可落地"的工程体系。
> 风格：知识卡片 + 伪代码 + 示例提示词；实现层面以"做法/职责"为主，不绑定具体代码。

---

## 1. 定位与适用边界

### 1.1 什么是企业级 Agentic RAG

企业级 Agentic RAG 是**多 Agent 编排 + 工具注册表 + 预算治理**的组合形态：

- **多 Agent 编排**：路由 / 规划 / 评审 / 纠错 / 校验各自成角色，用状态机而非手写循环驱动；
- **工具注册表**：检索能力（语义 / 混合 / 定向卷 / 多跳）以工具形态接入，决策与执行分离；
- **预算治理**：步数 / 轮数 / token / 墙钟 / 熔断五重护栏，全部集中在编排层统一施加。

与 Modular RAG 的本质差异：Modular 是"静态执行计划 + 有界升级"，Agentic 是"动态决策 + 证据驱动回环"。

### 1.2 选型决策树（什么场景该上 Agentic）

```
用户问题进入
 ├─ 单轮 / 单事实 / 低风险 → Naive / Advanced（一次检索 + 重排即可）
 ├─ 多策略组合 / 需要重写改写 / 需要升级校验 → Modular（静态计划够用）
 └─ 满足以下任一 → Agentic：
     ├─ 事实清单不固定，需要动态规划多次检索
     ├─ 检索结果需要"证据充分性"自校验（答不上来要会补）
     ├─ 需要跨卷 / 跨类型 / 多跳证据合成
     ├─ 复合问题（规则 + 算例 + 对比）
     └─ 成本与延迟可接受（Agentic 是四种范式里最贵的）
```

**决策原则**：Agentic 解决的是"检索充分性"问题，不是"所有问题"。能用静态计划解决的，不上状态机；能用一次检索解决的，不上多轮纠错。

## 2. 总体架构（四层 + 任务黑板）

### 2.1 分层视图

```
┌──────────────────────────────────────────────────┐
│ L3 交互层   意图解析 · 会话状态 · 多轮上下文 · 记忆注入  │
├──────────────────────────────────────────────────┤
│ L2 任务编排层（外层循环）                             │
│   任务图构建器 → 节点执行器 → 任务级校验器 → 缺口策略中心 │
├──────────────────────────────────────────────────┤
│ L1 检索闭环层（内层循环）                             │
│   路由 → 规划 → 检索 → 评审 → 校验 →（纠错 → 检索）     │
├──────────────────────────────────────────────────┤
│ L0 基础设施  工具注册表 · 证据池 · 预算账本 · 事件总线   │
└──────────────────────────────────────────────────┘

        ▲          ▲          ▲
        └────── 共享「任务黑板」──────┘
   任务图 + 证据池 + 已确认事实 + 预算记账 + 事件轨迹
```

### 2.2 任务黑板（唯一状态源）

黑板是两层循环协作的介质，所有组件**读写黑板而非直接相互调用**：

| 黑板分区 | 内容 | 写入者 | 读取者 |
|---|---|---|---|
| 任务图 | 子任务 DAG、节点状态 | L2 构建器 / 执行器 | L2 校验器、缺口策略中心 |
| 证据池 | 评审后的相关证据（跨轮累积、去重） | L1 评审 | L1 校验、L2 合成、生成器 |
| 已确认事实 | 校验通过的事实清单 | L1 校验 | L1 纠错（防重复检索） |
| 预算账本 | 各层 token/步数/费用记账 | 各层执行器 | 护栏、熔断、审计 |
| 事件轨迹 | 全量角色/工具调用流水 | 各层组件 | SSE 下发、评测、审计 |

**架构要点**：两层循环是"对等状态机"，不是"主从调用"。外层写任务图，内层写证据/缺口，黑板保证任何组件都能恢复上下文。

## 3. 角色体系

每个角色统一形态：**LLM 决策点 + 确定性规则回退**。LLM 只做判断，不做执行；解析失败/调用异常时，必须有可复现的规则回退，保证流程不被单次模型故障中断。

### 3.1 角色职责卡

| 角色 | 决策输出 | LLM 决策点 | 确定性回退 |
|---|---|---|---|
| 路由 Router | 要不要检索 / 生成策略（direct/citation/comparison） | 语义判断用户意图 | 默认"需要检索 + 引用" |
| 规划 Planner | 事实清单 + 首发检索计划（多路调用） | 拆解问题为事实项 | 事实清单 = 原查询，调用 = 单路语义检索 |
| 检索 Retriever | （执行角色）并行跑工具注册表 | 无 LLM 决策 | 纯执行 |
| 评审 Grader | 逐条证据相关性（保留/剔除）+ 缺口归纳 | 证据是否支撑事实 | 文本相似度粗筛，保高分 |
| 纠错 Corrector | 下一轮检索调用（换词/换卷/换工具） | 缺口如何补 | 用缺失事实直接作为查询词重查 |
| 校验 Verifier | 事实-证据支持度 → 可答/缺口清单 | 每条事实的证据充分性 | 缺失事实 = 规划事实全集 |

### 3.2 角色输入输出卡（以校验为例）

```
输入:  { 查询, 事实清单, 累积证据池, 已确认事实 }
输出:  { answerable: bool, missing_facts: [...], thought: str }
回退:  无 LLM 时 → 证据池为空则报全部事实缺失，否则按文本共现粗判
```

> 示例提示词（校验角色，非代码）：
> "你是一名事实核验员。下面给出用户问题、需要核验的事实清单，以及检索到的证据。请逐条判断：每条事实能否由证据直接支持。只依据证据，不要使用自身知识。输出格式：每条事实 → 支持/不支持，不支持时列出缺失的关键信息。"

### 3.3 角色纪律

- **决策与执行分离**：LLM 角色从不直接调检索，只产出"调用规格"，由执行层跑；
- **职责不越权**：评审只管证据相关性，不管答案好不好；校验只管证据充分性，不管任务做没做完；
- **失败有记**：每个角色连续失败达到阈值 → 熔断锁定为规则回退，并记录原因。

## 4. 工具注册表

### 4.1 工具接入规范

所有检索能力以"工具"注册进目录（catalog），统一元数据：

| 字段 | 说明 |
|---|---|
| action | 工具标识（语义 / 混合 / 定向卷 / 多跳…） |
| query | 查询词（由角色决策产出） |
| volume | 定向卷名（须在目录内，越界即拦截） |
| reason | 决策理由（缺口对应关系，用于审计） |

### 4.2 护栏（Guard）

| 护栏 | 规则 | 动作 |
|---|---|---|
| 参数校验 | 空查询 / 超长查询 / 卷名不在目录 | 拦截并记账 |
| 去重 | 同 (工具,查询,卷) 已执行过 | 拦截（防纠错重复检索） |
| 预算 | 剩余步数 / token / 墙钟 | 拦截并触发降级 |
| 熔断 | 相同参数连续失败 N 次 | 拦截（换参重试放行） |

护栏拦截**计入预算**（"含被拦截的调用"），防止模型用无效调用刷满预算。

### 4.3 并行与融合

- 一波内多路调用并行执行（上限可配）；
- 多路结果按 RRF（倒数排名融合）合并，跨轮 seed 作为额外一路参与融合；
- 融合后重排，再进评审——**先宽后严**：截断发生在评审之后而非之前，评审才是噪声过滤器。

## 5. 双层循环与层间契约

### 5.1 内层循环：单查询充分性闭环

```
route → plan → retrieve → grade → verify →（可答）→ 结束
                          ↑              │
                          └── correct ←──┘（缺口 → 纠错 → 再检索）
```

- 退出条件：可答 / 纠错轮数上限 / 步数预算 / 墙钟超时 / token 预算；
- 内层只对**它收到的那个查询**负责。

### 5.2 外层循环：任务闭环

```
意图解析 → 构建任务图 → 逐节点执行（触发内层或其它工具）→ 任务级校验 → 综合生成
                              ↑                              │
                              └──── 缺口策略中心决策 ──────────┘
```

- 退出条件：任务图全部 resolve 或所有缺口已被处理；
- 外层负责"用户的问题是否被完整解决"，内层负责"这个查询的证据够不够"。

### 5.3 层间结构化契约

内层契约（对一次检索查询）：

```
输入:  { query, context, seed_evidence, budget }
输出:  {
  evidence:      [...相关证据],
  verdict:       answerable | partial | insufficient,
  missing_facts: [...],
  confidence:    0~1,
  trace:         [...各角色事件],
  cost:          { tokens, calls, latency_ms }
}
```

外层契约（对一个任务）：

```
输入:  { user_intent, conversation_state, budget }
输出:  {
  task_graph:   [...节点],
  resolved:     {...节点证据与 verdict},
  gaps:         [...缺口 + 类型],
  final_answer: str,
  completion:   complete | partial | clarified
}
```

**契约纪律**：外层只读内层的 verdict/missing_facts 做决策，**不替内层判断证据够不够**；内层不替外层判断任务做没做完。

## 6. 任务图与缺口策略中心

### 6.1 任务图（外层的形式化载体）

外层循环不再"让模型自由发挥"，而是把任务分解为**节点 DAG**：

```
用户问题
 └─ 意图解析
     ├─ 节点A：规则查询（触发内层）
     ├─ 节点B：数据查询（触发内层，依赖 A 的"基数定义"）
     └─ 节点C：合成/计算（LLM 或计算工具，依赖 A+B）
```

每个节点是一个有状态的小循环：

```
planned ─► queried ─► verified ─► resolved（证据充分）
             │            │
             └────────────┴──► gap ─► 缺口策略中心
```

> 伪代码（节点执行循环）：
> ```
> while 任务图中存在未 resolve 的节点:
>     node = 下一个未处理节点
>     if node 是检索类:
>         result = 内层闭环(node.query, seed=黑板.证据池)
>         if result.verdict == answerable: node → resolved
>         else: node.gap = 缺口分类(result.missing_facts) → 转策略中心
>     if node 是合成/计算类:
>         用依赖节点输出执行 → resolved
>     记账 node.cost → 黑板.预算账本
> ```

### 6.2 缺口策略中心（决策表）

LLM 负责"缺口属于哪一类"，策略表负责"该类怎么处理"。决策表可配置、可审计、可评测：

| 缺口类型 | 判定信号 | 默认策略 | 次数上限 |
|---|---|---|---|
| 查询表达问题 | 换词后缺失项与已查内容语义重合 | 改写查询重查 | 1 |
| 数据确实缺失 | 重查后仍缺 + 元数据确认无此记录 | 如实上报 + 向用户追问 | 1 |
| 跨域缺口 | 缺口属于其它工具能力（计算/外部数据） | 转交对应工具 | 1 |
| 低价值缺口 | 不影响主问题核心结论 | 部分回答 + 明确标注 | 0 |

> 示例提示词（缺口分类，非代码）：
> "检索缺口分类任务：给定已检证据与缺失事实清单，将缺口归类为【查询表达问题】【数据确实缺失】【跨域缺口】【低价值缺口】之一，并说明理由。归类结果将决定下一步动作。"

**企业级要点**：缺口处理从"模型临场发挥"变成"确定性策略 + LLM 分类"，行为可预测、可回灌调参。

## 7. 预算治理体系

### 7.1 三层分账

| 账本 | 覆盖范围 | 关键指标 |
|---|---|---|
| 查询账本 | 单次内层闭环 | 步数 ≤ 8、token ≤ 8000、墙钟 ≤ 90s |
| 任务账本 | 单个用户任务 | 工具调用次数、子查询数、任务总 token |
| 会话账本 | 整轮对话 | 跨任务累计、超支熔断 |

**防级联超支**：外层每触发一次内层，先扣任务账本，再走查询账本——防止"每层各自达标、叠加超支"。

### 7.2 护栏矩阵

| 护栏 | 阈值 | 触发动作 |
|---|---|---|
| 步数上限 | 全轮工具调用总上限（含被拦截） | 停止检索，如实上报 |
| 纠错轮数 | 默认 2 轮 | 超出仍不足 → 上报缺口 |
| token 预算 | 角色 LLM 累计阈值 | 后续角色全部规则回退 |
| 墙钟超时 | 单查询 deadline | 不再发起新决策与工具波次 |
| 角色熔断 | 同一角色连续失败 2 次 | 该角色锁定规则回退 |

### 7.3 治理原则

- **预算全部集中在编排层**，角色/工具层不管预算（单一治理点）；
- **预算耗尽 ≠ 失败**，是"如实上报"——把缺口/状态如实告诉上层或用户，不沉默降级、不编造。

## 8. 证据与记忆管线

### 8.1 证据跨轮累积（防多轮遗忘）

每轮评审后的相关证据**合并**进证据池而非覆盖：

- 否则纠错第二轮会丢掉第一轮已确认的事实（如"张三在研发部"），导致校验误判缺口、纠错重复检索；
- 合并按内容去重、保持顺序。

### 8.2 已确认事实写回

校验判定"非缺失"的事实立即写回已确认集合：

- 后续轮次不再重复上报这些事实为缺失；
- 纠错基于已确认证据生成下一跳（如"张三=研发部 → 查研发部人数"）。

### 8.3 父块回填

- 评审/校验基于**精准子块**做判断；
- 最终注入生成器时，回填**父块全文**（子块定位、父块提供完整上下文）。

### 8.4 跨轮 seed 复用

- 每轮最终命中缓存为下一轮候选证据（经分数/相关性闸门过滤，防历史噪音污染）；
- 检索入口做指代消解（"他/这…"→ 具体对象），保证多轮追问语义正确；
- 前置语义路由结果复用：同一查询不二次路由，省一次 LLM 且保证生成策略前后一致。

## 9. 安全与合规

### 9.1 检索权限边界

- 定向卷检索必须校验卷名在目录内，越界即拦截；
- 敏感知识库分区可加"卷级权限"，检索执行前校验权限上下文。

### 9.2 内容治理（防编造）

所有检索结果块内嵌固定约束指令，强制"如实回答"纪律：

> 示例提示词（检索结果内嵌指令，非代码）：
> "请严格基于以上检索内容如实回答；若检索内容不足以回答，请明确说明缺失的关键信息，并礼貌地向用户追问补充，不要编造、不要依赖自身知识臆测内部数据。"

### 9.3 审计追踪

- 每角色/工具调用一条轨迹事件：角色、思想、动作、参数、命中数、时延、token 消耗；
- 全量留痕支撑：成本核算、行为审计、故障追溯、评测标注。

### 9.4 输入边界

- 空查询 / 超长查询在入口降级，不进入检索管线；
- 检索失败降级为"未命中"提示，不向生成层抛工具异常。

## 10. 可观测性与评测闭环

### 10.1 统一事件协议

两层循环共用一套事件 schema，汇入同一事件流：

```
task_id / node_id / role / action / query / verdict / latency_ms / tokens / note
```

事件类型覆盖：路由（running/done）、规划、检索步骤、评审、纠错、校验、证据下发、压缩指标、充分性结论。

### 10.2 双层评测口径

| 评测维度 | 指标 | 回灌作用 |
|---|---|---|
| 内层充分性 | verdict 准确率（误判可答/误判缺口） | 调纠错轮数、评审阈值 |
| 外层完整性 | 任务图 resolve 率、缺口处理正确率 | 调缺口策略表 |
| 综合 | 单任务成本、延迟、用户满意度 | 调双层预算 |

### 10.3 调参回灌闭环

```
评测指标 → 分析（缺口类型分布 / 纠错轮数分布 / token 趋势）
        → 调预算参数与策略表 → 回归评测 → 发布
```

**企业级要点**：优化是"数据回灌的持续循环"，不是"调一次提示词就完事"。

## 11. 失败模式与降级阶梯

全系统**唯一一条降级路径**，任何层失败只允许落到阶梯的某一级，禁止组件自创行为：

```
L1 失败（LLM 解析/调用异常）──► 规则回退（确定性重试）────────┐
L1 验证不通过 ──────────────► 缺口上报（missing_facts）────┤
L2 缺口策略执行后仍缺 ────────► 如实部分回答 + 追问 ─────────┤─► 收尾
全局预算耗尽 ───────────────► 停止并如实说明 ────────────────┘
```

| 失败场景 | 预期行为（用户视角） |
|---|---|
| 检索工具执行异常 | 告知检索故障，建议换关键词或稍后重试，不编造 |
| 检索未命中 | 说明缺失信息，礼貌追问补充依据 |
| 证据不足但预算耗尽 | 如实上报缺口，可答部分先行回答 |
| 模型连续失败 | 规则回退产出兜底结果，轨迹记录原因 |

**企业级要点**：失败是可预测的、有记录的、对用户诚实的。

## 12. 落地路径（从 Modular 渐进到 Agentic）

### 12.1 分期路线

| 阶段 | 目标 | 交付物 | 验收标准 |
|---|---|---|---|
| P0 | 内层闭环落地 | 状态机编排 + 角色体系 + 预算治理 | 单查询可答率、纠错轮数分布达标 |
| P1 | 契约化 | 内层结构化输出（verdict/missing_facts） | 缺口信息可被上层消费 |
| P2 | 外层形式化 | 任务图 + 节点状态机 | 复合问题多节点正确 resolve |
| P3 | 策略中心 | 缺口分类决策表 | 缺口处理正确率、行为可预测 |
| P4 | 治理与观测 | 三层分账 + 双层评测回灌 | 成本可核算、指标回灌调参闭环 |

### 12.2 渐进原则

- **先内后外**：内层充分性闭环是所有价值的基础，先把它做扎实；
- **契约先行**：任何两层协作改动，先定结构化协议再实现；
- **灰度切换**：Agentic 与 Modular 并行运行，按查询特征路由（决策树见 §1.2），用评测数据决定放量比例；
- **预算兜底**：Agentic 上线必须带预算治理，防止不可控成本。
