## 概述

智能体式 RAG（Agentic RAG）不再把「检索」当作固定的一步，而是把系统变成**主动决策者**：Agent 自主决定「要不要检索、检索几次、用什么方式检索、结果靠不靠谱、答案有没有文档支撑」。它在 Modular RAG「模块可编排」的基础上更进一步——控制流从「编译期定死的执行计划」升级为「运行期多角色动态决策的状态机」。

业界三条代表路线在此汇聚：

- **Self-RAG**：反思 token 决定「检索必要性 / 相关性 / 支撑度」；
- **CRAG**（Corrective RAG）：检索质量分级，差则纠错重检；
- **Adaptive RAG**：按查询复杂度动态选路。

本项目把三者统一进一个**多角色 Agent 编排**范式：角色分离 + 工具注册表 + 预算治理 + 双闭环。

## 为什么需要它

固定管道 RAG（naive / advanced）和模块化 RAG（modular 静态执行计划）都有一个共性：**决策在编译期就定型了**。由此产生三个工程痛点：

1. **路由误判即整路白跑**：复杂度路由一旦判错（如把多跳误判为单跳），整条链路按错误计划执行，没有运行时纠正机会；
2. **升级阶梯只能走一遍**：有界升级固定 1 轮（多路 → 定向 → 多跳），无法针对缺口多轮补检索；
3. **证据质量不可控**：命中即进上下文，无关块、重复块没有「逐条评审」环节，生成侧拿到的是未经质检的证据。

Agentic RAG 的价值：**决策移到运行期、每个角色独立判断、证据先评审后使用、预算内可反复纠错**。

## 核心思想：四支柱

| 支柱 | 要解决的工程问题 | 具体做法 |
|------|----------------|---------|
| **角色分离** | 一个模型干所有决策，抖动互相传染 | 决策拆为 5 个独立 LLM 角色（路由 / 规划 / 评审 / 纠错 / 校验），各自独立场景、独立规则回退、独立熔断；检索执行不设 LLM 角色（决策与执行分离） |
| **工具注册表** | Agent 乱调工具、重复调用、越权 | 库内检索能力封装为 4 个工具，注册表白名单 + 单工具限次 + 跨波去重 + 非法卷降级 + 并行波次五类护栏统一治理 |
| **预算治理** | 自主循环不可控、烧 token | 步数 / 纠错轮数 / token / 墙钟超时 / 单工具上限 / 角色熔断全部可配置，超限优雅降级而非硬失败 |
| **双闭环** | 检索质量与答案质量都缺质检 | 证据评审闭环（CRAG）：逐条评审 + 缺口归纳 → 不足则纠错补检索；答案校验闭环（Self-RAG）：事实-证据支持度矩阵 → 可答直接答 / 不足如实澄清 |

## 角色协议（五角色）

| 角色 | 对应范式 | 职责 | 输出（JSON） | 规则回退 |
|------|---------|------|-------------|---------|
| **路由 Router** | Adaptive-RAG | 边界判断：要不要检索 / 生成策略 / 定向语料提示 | `retrieval_need / generation_mode / target / reason` | 保守全检索 + 引用生成 |
| **规划 Planner** | — | 问题 → 事实清单 + 首发多路检索计划 | `facts[] / calls[] / reason` | 单事实 + 混合检索（链式查询 → 多跳） |
| **评审 Grader** | CRAG | 逐条证据相关性评分 + 归纳缺失事实 | `relevant[]（下标）/ missing_facts[] / reason` | 词法共现粗评（2 字词 ≥2 或分数 ≥0.5，宽松防误杀） |
| **纠错 Corrector** | CRAG | 证据不足时的纠错波决策（换表述 / 换卷 / 换工具） | `calls[] / reason` | 每缺失事实一路：未用过的定向卷优先，否则混合检索 |
| **校验 Verifier** | Self-RAG | 事实-证据支持度矩阵 → 可答性 | `answerable / missing_facts[] / reason` | 词法覆盖判定（2 字词覆盖 ≥50%） |

关键设计：

- **决策 / 执行分离**：检索执行不设 LLM 角色——决策智能集中在规划 / 纠错，执行治理在工具注册表，执行层零 LLM 成本；
- **规则回退兜底**：无聊天 Key / LLM 输出不可解析 / 调用异常 → 对应角色规则回退（在轨迹记 `note`），链路不中断；
- **熔断**：同一角色连续 2 次决策失败 → 锁定规则回退，不再消耗 LLM 调用；
- **越界防护**：动作白名单过滤、证据下标越界剔除、非法生成模式归一为引用回答。

## 工具注册表

把库内检索能力封装为 4 个带治理的工具：

| 工具 | 说明 | 适用 |
|------|------|------|
| `search` | 纯向量检索 | 语义相似 / 同义改写类查询 |
| `hybrid` | 混合检索（语义 + 关键词，含规模规范词扩展） | 制度条款 / 表格 / 含编号数字 |
| `volume_search` | 定向卷内检索（卷名须取自卷目录） | 档案 / FAQ / 案例 / 版本对比 |
| `multi_hop` | 多跳规划-执行-验证 | 实体链 / 流程链问题 |

五类护栏：

1. **白名单拦截**：注册表外动作直接拦截不执行；
2. **单工具限次**：超调用上限拦截（保留决策意图，不执行，仍计入预算计数）；
3. **跨波去重**：同一「工具 + 查询 + 卷」已正常执行过 → 后续波次拦截（同波不去重，允许首发多路撞车）；
4. **非法卷降级**：定向卷检索的卷名不在目录 → 降级全库检索（保留检索意图）；
5. **并行波次**：一波多路调用并行执行（默认上限 4），首发按事实清单并行、纠错波同理。

辅助能力：定向卷结果多样性截断（同模板块只留代表，防挤占融合配额）、跨轮 seed 复用闸门（上轮已验证命中经分数门槛 / 相关性把关 / 限量 5 条后作本轮候选证据）。

## 预算治理

| 预算 | 配置项 | 默认 | 超限行为 |
|------|--------|------|---------|
| 步数 | `rag_agent_max_steps` | 8 | 强制结束检索循环（含被护栏拦截的调用） |
| 纠错回环 | `rag_agent_correction_rounds` | 2 | 停止纠错，交校验角色终判 |
| 墙钟超时 | `rag_agent_timeout_s` | 90s | 不再发起新的 LLM 决策与工具波次 |
| token 预算 | `rag_agent_token_budget` | 0（不限，可配置收紧） | 达阈值后续角色全部规则回退 |
| 单工具上限 | `rag_agent_tool_call_cap` | 3 | 该工具后续调用被拦截（多跳固定更紧为 1） |
| 并行度 | `rag_agent_parallel` | 4 | 波内排队执行 |

第 7 项治理是**熔断**：角色连续 2 次失败 → 锁定规则回退。所有预算在编排层统一施加（角色 / 工具层不管预算），超限优雅降级——降级后仍产出确定性结果，并在轨迹记 `note`，可用性优先。

## 状态机与证据管线（伪代码）

Agentic RAG 的核心是一条**双闭环状态机**：

```
ROUTE（要不要检索？）
 ├─ 检索无关 → END（寒暄 / 常识直接生成）
 └─ 需要检索 → PLAN（事实清单 + 首发计划）
                  → RETRIEVE（并行波次）
                  → 证据管线：RRF 融合 → 重排 → GRADE（逐条评审）
                       ├─ 缺口且纠错预算有余 → CORRECT → 回 RETRIEVE（纠错闭环）
                       └─ VERIFY（支持度矩阵）
                             ├─ 可答 → 压缩 → 父块回填 → 生成
                             └─ 预算耗尽仍不足 → 如实上报 CLARIFY（不编造）
```

对应伪代码：

```python
# Agentic RAG：多角色状态机（伪代码，非实际实现）
async def agentic_rag(query):
    route = await Router.decide(query)                    # 要不要检索 / 生成策略
    if not route.retrieval_need:
        return await generate(query)                      # 寒暄 / 常识直接答

    plan = await Planner.plan(query)                      # 事实清单 + 首发计划
    for round in range(0, max_rounds):                    # 预算内的纠错回环
        hits = await ToolRegistry.execute_wave(plan.calls)     # 并行波次 + 护栏
        kept, missing = await Grader.grade(query, hits)        # 逐条评审 + 缺口
        if missing and budget_left(round):
            plan.calls = await Corrector.correct(query, missing)   # 按缺口定向补检索
            continue
        answerable = await Verifier.verify(query, kept)    # 支持度矩阵
        break

    if not answerable:
        return await clarify(missing)                     # 如实上报缺口，不编造
    return await generate(query, kept)                    # 带证据生成
```

- **证据评审闭环（CRAG）**：评审角色逐条判断相关性、剔除无关块、归纳缺口；缺口且纠错预算有余 → 纠错角色按缺口定向补检索（换表述 / 换卷 / 换工具，禁止重复已执行调用）→ 回检索；
- **答案校验闭环（Self-RAG）**：校验角色按「回答所需事实 × 当前证据」的支持度矩阵判定——可答直接答；预算耗尽仍不足 → **如实上报缺口并追问澄清，绝不编造**；
- **跨轮记忆**：评审 / 纠错 / 校验都结合「先前轮已确认的证据 / 事实」，避免多轮遗忘导致重复检索（如已确认「张三在研发部」，缺口只报「部门人数」，下一跳直接查「研发部 在职人数」）。

## 角色 Prompt 设计

五角色全部是「结构化 JSON 输出」的低延迟轻量决策（`qwen3.5-flash / enable_thinking=False`，关闭思考以省延迟），各角色独立命名 LLM 场景、统一低温度小输出长度：

| 角色 | temperature | max_tokens |
|------|-------------|-----------|
| 路由 | 0.1 | 250 |
| 规划 | 0.2 | 500 |
| 评审 | 0.1 | 500 |
| 纠错 | 0.2 | 400 |
| 校验 | 0.1 | 400 |

统一约定：**只输出严格 JSON、不要任何多余文字**；输出不可解析或动作越界时，对应角色走确定性规则回退（见上文角色协议），链路不中断；同一角色连续 2 次决策失败则熔断锁定规则回退。

## 收益与边界

**收益**

- 自主决策：常识直接答、复杂问题多轮检索，收敛靠预算而非拍脑袋；
- 证据先评审后使用（CRAG）：无关块进上下文前被剔除，缺口驱动定向补检索；
- 无据可依不硬答（Self-RAG）：事实-证据支持度矩阵把关，防幻觉；
- 预算治理：步数 / 纠错轮数 / token / 超时 / 单工具上限多维可控，超限优雅降级；
- 全程可观测：每次决策带思想 / 动作 / 命中 / 时延 / token / 护栏备注，前端按角色渲染时间线。

**边界 / 局限**

- 每查询多次角色 LLM 调用，**延迟与成本高于 modular**（低参数模型 + 预算治理控制）；
- LLM 决策抖动靠四层兜底：JSON 解析失败 → 规则回退、护栏拦截、预算降级、校验闸门兜底澄清；
- 工具范围**仅限库内检索**（不做写操作、不调外部 API），是检索范式而非通用 Agent；
- 对语料覆盖要求高：知识库确实缺失时只能如实澄清，无法凭空补全。

## 企业级应该怎么做

企业生产环境对 RAG 的要求远超「检索 + 生成」本身。Agentic 形态在带来自主决策能力的同时，也带来**多次角色 LLM 调用、运行期黑盒决策、敏感数据进上下文**等新风险，因此企业落地还需补足以下横切能力：

### 1. 多级缓存

- **做法**：三级缓存——查询级缓存（相同 / 近似问题直接命中历史答案）、Embedding 缓存（相同文本复用向量）、检索结果缓存（相同查询 + 知识库复用结果）；
- **必要性**：Agentic 每查询多次角色 LLM 调用，成本与延迟远高于单次检索；企业高频重复问题占比大，缓存命中可整体跳过编排链路，是成本治理的第一道闸。

### 2. 规则路由 / 快速通道

- **做法**：廉价的规则 / 命中式快速路由处理 FAQ、命令、寒暄、高频问题（免 LLM、毫秒级返回），未命中再降级到语义路由慢路，两级配合；
- **必要性**：LLM 路由质量高但贵且慢；对可枚举 / 高频输入先用规则快路，可显著降低平均延迟与成本，也是 LLM 不可用时的兜底。

### 3. 监控告警

- **做法**：对 token / 时延 / 角色调用 / 护栏拦截 / 预算超限 / 熔断 / 纠错空转等指标采集、看板展示、阈值告警；
- **必要性**：Agentic 是运行期多角色动态决策，天然黑盒；没有监控就发现不了预算被耗尽、角色熔断、纠错空转等异常，也无法量化改动效果。

### 4. 检索级权限与数据隔离

- **做法**：检索结果按角色 / 部门 / 密级过滤与脱敏后再进上下文；
- **必要性**：企业知识库常含敏感数据，检索层不做越权过滤，会把不可见内容直接带入生成上下文，构成数据泄露面。

### 5. 多知识库路由（D2 数据源路由）

- **做法**：按数据源 / 知识库选库路由、跨库融合；
- **必要性**：企业往往有制度库、产品库、FAQ 库等多个知识源，单库路由只能覆盖单一领域。

## 本项目的做法

**定位说明**：本项目是**个人实践项目**，受精力所限，**只为验证 Agentic RAG 通路可行性**——多角色状态机、工具注册表、预算治理、双闭环能否跑通，SSE 事件链能否逐事件串起。因此上一节的 5 项企业级横切能力（多级缓存、规则路由 / 快速通道、监控告警、检索级权限与数据隔离、多知识库路由）**暂未实现**；若用于企业生产，需按「企业级应该怎么做」补齐，各条目的必要性已随之上文说明。

本项目把 Agentic RAG 落地为多方案框架中的 **agentic** 方案（与 naive / advanced / modular 并列，侧边栏可切换）——继承 advanced **仅取底层原语**（入库分块 / 重排 / 压缩 / 父块回填），编排完全独立：多角色状态机取代静态执行计划，不再受 modular 模块链约束。

- **五角色独立决策**：路由 / 规划 / 评审 / 纠错 / 校验各自独立命名 LLM 场景、独立规则回退、独立熔断；无聊天 Key / 超预算 / 超时 / 熔断时确定性规则回退，离线可跑；
- **工具注册表**：4 个库内检索工具 + 五类护栏统一治理；检索执行不设 LLM 角色（决策在规划 / 纠错，执行在注册表）；
- **证据管线**：RRF 融合（定向卷先多样性截断、跨轮 seed 额外一路）→ 重排 → 逐条评审 → 纠错回环 → 支持度校验；
- **前置与后处理**：指代消解 + 跨轮 seed 复用（与 modular 同款）；压缩、父块回填复用底层原语；
- **可观测事件**：检索事件串为 `classify → plan → 逐工具步 agent_step → grade → correct → verify → retrieve → compress → answerability`，前端检索卡片依次展示「语义路由 → 规划 → 多 Agent 逐步执行 → 证据评审 → 纠错 → 校验 → 知识库检索 → 上下文压缩」；每次角色决策携带思想 / 动作 / 命中数 / 时延 / token / 护栏备注，可复现、可核算；
- **与 modular 的对照**：modular 是「静态执行计划 + 有界升级 1 轮」；agentic 是「动态状态机 + 预算内纠错回环（默认 2 轮）+ 逐条证据评审」——路由误判有运行时纠正机会，升级不再只能走一遍，证据质量可控。

## 演进方向

- **需要多知识库 / 外部数据源** → 工具注册表扩展新检索工具（注册新工具描述 + 执行器即可，角色与编排不改）；
- **需要写操作 / 外部 API 调用** → 演进为通用 Agent（当前刻意限定库内只读检索）；
- **需要更强规划** → 与 plan_execute / reflection 等推理模式联动（[plan-execute.md](plan-execute.md) / [reflection.md](reflection.md)）。
