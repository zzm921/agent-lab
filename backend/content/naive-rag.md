## 概述

Naive RAG（朴素 RAG / Vanilla RAG / Standard RAG）是 RAG 的最原始形态：**固定三步**——把文档切块向量化入库，用户提问时用向量相似度召回 Top-K 片段，拼接进 prompt 交给 LLM 生成。它是 RAG 一切的**原点与基线**，后续所有范式都是对它的缺陷打补丁。

## 为什么需要（RAG 的原点）

2020 年 Lewis 等人在《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》中提出 RAG，核心思想是给大模型装上一个**可随时检索的外部非参数记忆**：

- LLM 把事实存进参数（参数记忆），但无法精确操作知识、难给决策出处、世界知识难更新、会幻觉；
- RAG 让「知识」从参数中解放出来，变成**可修订、可访问、可解释**的外部索引，端到端参与生成；
- 朴素形态的意义在于**先跑通最小闭环**：验证「检索增强生成」这条路可行，成为后续所有优化的度量基线。

## 核心流程

```
离线（建库）：
  加载文档 → 切块 → 向量化 → 存入向量库
在线（问答）：
  Query 向量化 → 向量库 Top-K 相似度召回 → 拼接上下文 → LLM 生成
```

五个步骤、四个关键参数，就是 Naive RAG 的全部：

| 环节 | 做什么 | 关键决策 |
|------|--------|---------|
| 切块 | 把长文档切成可检索的片段 | chunk 大小（检索粒度）、重叠 overlap（减少语义断裂） |
| 向量化 | 把文本映射为稠密向量 | Embedding 模型选择（语言适配、维度、成本） |
| 入库/索引 | 存入向量库供相似度检索 | 向量库选型（Qdrant / Milvus / FAISS） |
| 检索 | 对 Query 向量做 Top-K 近邻搜索 | 相似度度量（余弦 / 点积）、Top-K 取值 |
| 生成 | 把「检索片段 + 问题」拼进 prompt 交给 LLM | 上下文组装方式、引用约束 |

## 收益（优点）

- **架构极简**：开发、部署、维护成本最低，最容易跑通 POC；
- **响应快**：运算量小，适合延迟敏感场景；
- **普适性**：不依赖任务定制，接入任意文档即可问答。

## 局限（为什么「朴素」）

- **召回噪声**：向量相似度 ≠ 相关性，相似度最高的片段未必是答案所在，噪声直接进入上下文；
- **上下文窗口污染**：检索到的所有文本都塞进 prompt，模型有效注意力有限，超出的部分被稀释，反而干扰作答；
- **关键词盲区**：纯语义匹配命中不了专有名词、编号、精确句式（BM25 能做的它做不了）；
- **关系盲区**：文档被切成孤立片段，无法处理跨 chunk、跨文档的关联与多跳问题；
- **无评估闭环**：没有检索质量（召回/准确）与生成质量（忠实度/幻觉）的独立度量，优化无从下手。

## 适用场景

数据规模小、问题类型单一、对延迟要求极高、先验证可行性——例如内部 FAQ 问答、轻量文档检索的 MVP。**如果你的场景还在这个范围内，先不要急着升级。**

## 本项目的做法

本项目把 Naive RAG 实现为**多方案框架中的最简基线**：内置语料为虚构「科创公司员工行政、考勤、福利与差旅全管理制度」（长文本、高冗余、规则嵌套、信息碎片化），按方案写入独立的 Qdrant 集合 `knowledge_naive`（未配置 Qdrant 时回退内存检索）。

- **切块**：固定长度切块（默认 150 字符、无重叠），长规则被硬切为多块——直接演示「固定切块切断长文本语义」的缺陷；
- **入库**：`DashScope text-embedding-v3` 对每个切块生成稠密向量，写入本方案专属集合；
- **检索**：查询向量化后对集合做纯稠密余弦相似度 Top-K 召回——不做查询改写、不做混合检索、不做重排、不做推理，保持最朴素的基线；
- **对比**：同一份语料被后续各代方案（Advanced 混合检索 / Modular 路由多跳 / Graph 实体图谱 / Agentic 规划计算）逐步升级，侧边栏切换方案即可看到检索卡片与回答差异逐代提升。

**一个直观的对照样例**：问「发票什么时候交」——即便语料已补充独立的「发票提交时限：…15 个自然日内上传 OA」声明，naive 的纯稠密固定切块仍可能因**问法与原文措辞不一致**（「交」vs「提交时限」）而召回不准；advanced 的 Query 重写会生成「发票提交时限规定 / 发票报销截止日期规定 / 发票上交流程及时限要求」等变体，配合 ES BM25 关键词路精确命中。同一问题切换 naive / advanced，检索卡片即可看到改写变体与召回差异——这就是「关键词盲区」的具象演示。

> 它是其余方案的度量基准：advanced / modular / graph / agentic 的所有优化都以「比 naive 召回得更准、答得更全」为目标。当前已落地 naive / advanced / modular 三方案，graph / agentic 仍在同一框架上规划扩展。

## 推荐 Prompt

Naive RAG 只有一条固定链路（切块 → 向量 Top-K 召回 → 生成），因此只需**一个生成作答 Prompt**。它不依赖任何检索前/检索后智能，是后续所有 RAG 的生成基线。

### 1. 基础作答（全方案共用的基线）

**作用**：把检索命中的 Top-K 片段 + 用户问题交给 LLM 作答，要求有据可依、可标注来源。本项目同样把命中注入主对话用户消息（注入式增强）。

**推荐注入模板**：

```
{用户原始问题}

【知识库检索结果（{方案名}）】
[相关度 0.91] {命中片段1}
[相关度 0.87] {命中片段2}
...

请优先基于以上检索内容回答；若内容不足以回答，再结合自身知识补充。
回答时如内容来自检索片段，请标注对应来源。
```

**要点**：这是朴素 RAG 的全部「提示工程」——naive 的局限（召回噪声、上下文污染）本质是「检索端」的问题，改 Prompt 只能缓解、无法根治，升级要落在检索链路（见下方演进方向）。

## 演进方向：如何升级到 Advanced RAG

Naive 的每一个痛点，几乎都对应 Advanced RAG 的一个优化手段：

| Naive 的痛点 | Advanced RAG 的对应补丁 |
|-------------|------------------------|
| 查询问法与语料表达不一致，漏召 | 查询改写、Multi-Query、HyDE |
| 纯向量召回噪声多 | 混合检索（向量 + BM25）+ 多路融合 |
| 上下文窗口污染 | Rerank 精排 + 上下文压缩 |
| 所有问题一刀切 | 意图分类 / 路由，按查询复杂度分流 |

升级路径详见 [advanced-rag.md](advanced-rag.md)。
