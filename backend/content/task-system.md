## 概述

任务系统是 Agent 的「施工管理」底座：把用户的复杂目标先 **todo write**（拆解成原子子任务、写入带状态机的清单），再经 **任务单** 为每个子任务指定执行者与上下文，由 **调度器** 按依赖并行/串行执行，**追踪** 状态流转并把结果按 task id 归位，最后 **汇总** 合并产出、决定是否再拆一轮。

它同时是 plan_execute（线性清单）与 multi_agent（角色协作）的共同地基：plan_execute 的 plan 是它的线性特例，multi_agent 的任务单分派是它的协作形态。

## 为什么需要

- **纯对话流不可追踪**：任务做到哪一步、哪些失败、哪些可并行，不能只靠模型"心里有数"，需要显式数据结构支撑可审查、可恢复；
- **并行需要显式依赖**：只有把子任务的 `deps` 写出来，调度器才知道谁可以同时跑、谁必须等谁；
- **失败要可定位可恢复**：per-task 状态机让失败只重做失败项，而不是整盘重来；
- **可观测**：进度、产出、负责人按任务维度可见可回溯。

## 通用设计思路（五环节闭环）

```
todo write（拆解 + 写入清单）→ 任务单（指定执行者）→ 调度（并行/串行波次）
  → 追踪（状态流转 + 结果按 id 归位）→ 汇总（synthesize + decide → 再拆 or 收尾）
```

### 1. Todo Write：拆解 + 状态机

todo write 是任务系统的「入口与大脑」：把目标拆成**原子子任务**写入共享清单，并持续维护每个子任务的状态。拆解质量决定后续分派、调度、汇总的上下限。

#### 拆解策略（四个参数）

| 参数 | 原则 |
|------|------|
| **粒度** | 拆到「执行者一步能完成」——太粗无从下手，太细拆解成本比执行还高 |
| **上限** | 设单轮拆解数量上限，防「拆解爆炸」；超限则分批或按优先级裁剪 |
| **依赖** | `deps` 显式声明，无依赖可并行、有依赖须串行 |
| **归属** | 每个子任务最终能映射到一个执行者（同一模型，或某个专业 Worker） |

另有一条铁律：**任务缺少执行必需的关键信息（出发地/预算/偏好等）时，把「向用户确认关键信息」列为一个子任务**，而不是假设或编造缺失信息。

#### 数据结构

```
todo = [
  { id: "t1", desc: "调研主流 AI 助手定价",   deps: [],     status: "pending", assignee: "researcher", result: null },
  { id: "t2", desc: "基于 t1 结论给技术选型", deps: ["t1"], status: "pending", assignee: "developer",  result: null },
]
```

- `id`：唯一标识，事件流与结果归位的锚点；
- `desc`：可独立完成的子任务描述；
- `deps`：依赖的前置任务 id 列表；
- `status`：状态机当前值；
- `assignee`：执行者（单智能体=自己；多智能体=角色）；未指定则稍后由任务单补齐；
- `result`：产出摘要/引用，供汇总层归位。

#### 状态机（统一流转规则）

```
pending → dispatched → running → done
                        ↘ failed
failed → pending（重派：换执行者 / 改措辞）或 保留 failed（如实上报缺口）
```

- `pending → dispatched`：被调度器选中派发时；
- `dispatched → running`：执行者开始执行；
- `running → done`：产出可用；
- `running → failed`：执行失败 / 超时 / 轮数超限（**强制收敛**，防悬挂）。

关键点：**状态机必须全链路共享**——拆解层写入、调度层推进、追踪层展示，都认同一套 `pending/dispatched/running/done/failed`，否则不可追踪。

#### 触发时机（什么时候写）

| 时机 | 触发条件 | 动作 |
|------|----------|------|
| **T0 开局** | 新任务进入 | 首次拆解写入 todo，全部 `pending` |
| **T1 失败重规划** | 某子任务 `failed` | 只重生成「未完成 / 失败」的剩余项，**保留已完成项**，不整盘推翻 |
| **T2 汇总发现缺口** | synthesize 后 `decide` 判定信息不足 | 缺口写回 todo（新增 pending 项），再走分派 |

每次写入/更新都发射 `todo_created / todo_updated` 事件，前端时间线据此渲染勾选进度。

### 2. 任务单：todo → 谁做

todo 只写「做什么」，任务单补上「谁做 + 带什么上下文」：

```
ticket = { id: "t1", role: "researcher", task: "调研主流 AI 助手定价", context: "", deps: [] }
```

- 任务单把子任务**路由到专业角色**（多智能体），或标记为**自执行步骤**（单智能体）；
- 任务单携带**上下文**，保证执行者拿到的是可独立完成的完整输入。

### 3. 调度：按依赖排波次

```
波次1（并行）：t1, t3, t4          # 无互相依赖
波次2（并行）：t2, t5              # 依赖波次1 的产出
```

- 同一波次的子任务**并行**执行（延迟 = 取最长而非累加）；
- 跨波次**串行**，等待前置产出。

### 4. 追踪：状态流转 + 结果归位

```
t1: pending → dispatched → running → done      结果写入 results["t1"]
t2: 等 t1 done 后才 dispatched → …              失败 → failed（重派 or 上报缺口）
```

关键点：**结果按 task id 归位**——并行返回是乱序的，必须靠 id 对齐，不能按对话顺序。

### 5. 汇总：synthesize + decide

```
results = { t1: "…", t3: "…", t4: "…" }
→ synthesize 合并为阶段性答案
→ decide：全部关键子任务已覆盖？是 → 输出；否 → 缺口写回 todo，再走一轮
```

## 关键设计点

| 设计点 | 要点 |
|--------|------|
| **原子粒度** | 子任务是执行者可一步完成的最小单元 |
| **依赖即并行边界** | `deps` 是并行/串行的唯一依据，避免执行者凭感觉乱并行 |
| **统一状态机** | 所有环节共享 `pending/dispatched/running/done/failed`，追踪层才可观测 |
| **按 id 归位** | 结果与子任务通过 id 关联，不依赖执行顺序 |
| **失败收敛** | 失败项可重派（换执行者/改措辞）或如实上报缺口，不掩盖不编造 |

## 推荐 Prompt（示例）

### ① Todo 拆解器

```
你是任务拆解器。把用户的复杂目标拆成若干原子子任务：
1. 每个子任务是执行者可一步完成的最小单元；
2. 显式标注子任务间的依赖（谁先谁后、谁的结果被谁用）；
3. 可并行的子任务之间不要互相依赖；
4. 若任务缺少执行必需的关键信息（如出发地、预算、偏好），
   把「向用户确认关键信息」列为一个子任务；
5. 每个子任务必须能独立分配给某个执行者完成。
输出格式：每行一个子任务，格式为「[依赖任务id列表] 子任务描述」。
```

### ② 状态更新（执行者向 todo 回写）

```
完成当前子任务后，更新任务清单：
- 已完成的子任务标记 done，并附一行关键产出；
- 未能完成的子任务标记 failed，说明失败原因（不要编造成功）；
- 若发现清单缺失的必要步骤，新增为 pending 子任务并标注依赖。
```

### ③ Decide（汇总后是否再拆）

```
基于已归位的结果判断：
1. 全部关键子任务是否已 done 且产出可用？是 → {"continue": false}；
2. 仍有缺口（failed 项 / 新发现的必要步骤）→ {"continue": true, "next_tasks": [任务单列表]}；
3. 不得重复创建已 done 的任务。
输出必须严格是 JSON。
```

## 本项目的做法（目标）

先落地 todo write（本阶段），再逐步接入任务单 / 调度 / 汇总。

**todo write 落地改造**

- **状态结构**：plan_execute 的「线性步骤清单」升级为 todo（每项 `id / desc / deps / status`），去掉单一进度游标，改由**逐项状态**驱动推进；
- **拆解输出**：规划器系统提示要求输出带 id 与依赖标注的子任务列表，解析器按行解析为 `TodoItem` 写入状态，首轮拆解发射 `todo_created`；
- **执行推进**：每完成一项把该项置 `done`（附一行关键产出）；失败置 `failed`；轮数/超时超限时**强制收敛**为 `failed`，防悬挂；
- **失败重规划**：只重生成「未完成 / 失败」的剩余项，**保留已完成项**（不整盘推翻）；
- **事件**：`plan` 事件升级携带 `items`（含逐项状态），前端时间线按 `item.status` 渲染勾选 / 失败 / 进行中；
- **护栏**：单轮拆解数量上限，防拆解爆炸。

**后续阶段**（任务单 / 调度 / 追踪 / 汇总，见上文各节）

- **任务单**：multi_agent 的 worker 派发入参从裸字符串升级为任务单 `{id, role, task, context?, deps?}`（role 为角色标注，deps 声明依赖），事件按 task id 归位；
- **调度**：无依赖子任务同轮并行执行，依赖跨波次串行；
- **追踪与汇总**：共享状态机 + 按 id 归位 + synthesize/decide 闭环，事件流 `todo_created → task_dispatch → task_done → todo_updated → synthesize`；
- **护栏**：任务数上限、单任务超时/轮数上限，防止拆解爆炸与单任务死循环。

## 收益与边界

**收益**

- 可追踪可审查：任务清单 + 进度 + 产出全程可见；
- 并行安全：依赖显式化，并行不越界；
- 失败局部恢复：只重做失败项，不整盘重来；
- 跨模式复用：plan_execute 与 multi_agent 共用同一套任务管理。

**边界 / 局限**

- 拆解与状态维护有成本，简单任务用它反而低效；
- 任务间数据传递需要物化（结果归位后的引用），复杂依赖会放大上下文；
- 状态机正确性依赖执行者回写诚实，需护栏兜底（如超时强制 failed）。

## 演进方向

- **子任务产物物化**：中间结果落盘为文件/引用，避免全部堆进上下文（见 [context-mgmt.md](context-mgmt.md)）；
- **任务级预算**：per-task token / 轮数 / 超时治理；
- **依赖 DAG 可视化**：把波次调度画成图，直接展示并行路径。
