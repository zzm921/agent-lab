## 概述

文本语义检索答不了"上月报销总额""部门人数排名"这类聚合计算问题。Text-to-SQL 把自然语言转成 SQL 查库表，覆盖统计 / 排名 / 跨表聚合类问题，让检索从"文本语义"走向"结构计算"。

## 为什么需要它

RAG 检索的是"语义相似"，SQL 算的是"结构事实"。统计类问题语义检索只能"猜答案"，SQL 能"算答案"。但企业级落地有一条残酷规律：**学术榜单（Spider / BIRD）上 80%+ 的准确率，在未经工程化治理的真实数仓中往往暴跌到 30% 以下**。差距不在模型能力，而在缺少"语义约束 + 工程护栏"。

## 企业级通用设计思路

核心结论：企业级 Text2SQL **不是"一次 Prompt 直接生成 SQL"，而是"带语义约束的多阶段受控查询管线"**。直接把全库 DDL 塞给 LLM 让它生成 SQL，会撞上这些真实的坑：

| 难点 | 具体表现（企业真实场景） | 企业级应对 |
| --- | --- | --- |
| **Schema Linking（Schema 幻觉）** | 真实数仓上千张表、字段晦涩（如 `tbl_f_001_v2`），全塞 Prompt 会 Token 爆炸、噪音大、模型"迷失在中间"，还会捏造不存在的表 / 字段 | Schema 级联检索 + 字段剪枝：混合检索（稠密向量 + BM25）先召回 Top 3~5 张候选表，再剪到 10~15 个强相关字段 |
| **Value Linking（实体值对齐）** | 用户说"苹果手机"，库中真实枚举是 `brand_en='Apple' AND category='SmartPhone'`；"线上""华东"要命中真实取值 | 为高频低基数维度（省份 / 品牌 / 类目）构建倒排值词典 / 前缀索引，生成前注入真实枚举值 |
| **指标口径（Metric Drift）** | "活跃用户""流失率"定义分散：是 30 天未登录还是 90 天？分母是期初还是期末？不同部门口径不同 → 同一问题算出多个答案 | 语义层 / 指标层统一口径，模型只"翻译"到指标查询语言（MQL），不自行推断计算逻辑 |
| **复杂 JOIN** | 多表关联路径难推断，易犯 Fan Trap / Chasm Trap，聚合层级错乱（JOIN 缺失是错误主因） | 语义层把关联关系显式建模（外键属性化、Join Graph），或由确定性编译引擎生成 JOIN 片段，不交给模型"猜路" |
| **相对时间表达** | "本月""最近 30 天"依赖**当前日期**才能翻译 | 请求时动态注入当前日期 / 星期 / 季度 |
| **方言差异** | StarRocks / ClickHouse / Trino / Spark / MySQL 语法各不相同 | 注入目标方言规则 + 方言护栏（Dialect Guardrails） |
| **生成不可信与越权** | 全表扫描打爆集群、跨租户读敏感薪资、被注入删表指令 | 只读隔离 + AST 静态审查 + 沙箱 Dry-Run + HITL 熔断 |

### 企业主流技术路径（四条路线）

| 路线 | 原理 | 准确率 | 代价 |
|------|------|--------|------|
| **预制 SQL / 问答对** | 人工预置 SQL 绑定问题模板，向量召回命中 | 预置问题内 100%，未命中回退 NL2SQL | 维护成本指数级增长，3 套系统 / 100+ 口径即失控 |
| **Text2SQL + 宽表** | NL2SQL 引擎 + 人工预制宽表，单表查询为主 | 单表 ~90%，跨 3 表以上普遍 <70% | 宽表"上下文固定"，无法动态跨域，随业务变更维护失控 |
| **预置指标平台** | 预先定义指标计算逻辑（dbt MetricFlow / Cube） | 预设指标内 100%，未定义指标无法回答 | 指标扩展成本陡增，只适合口径高度标准化组织 |
| **本体语义层** | 本体图谱建模"对象-属性-关系"，跨表跨库跨域（Palantir / UINO 等） | 开卷 ~100%，闭卷 ~95% | 需先构建本体语义层，治理投入前置 |

### 工业级四阶段架构（受控查询管线）

```
Schema 链接与剪枝 → 实体值对齐 → 受约束生成 → 验证与自愈
```

1. **Schema 链接与剪枝**：混合检索（稠密 + 稀疏）从数千张表召回候选集，再按提问相关度剪到关键字段，只暴露这一小撮上下文给模型；
2. **实体值对齐（Value Linking）**：倒排值索引命中物理库真实枚举，并注入指标标准公式（如"复购率 → `SUM(repeat_uv) / NULLIF(SUM(total_uv),0)`"）；
3. **受约束生成（CoT + Dialect Guardrails）**：输出结构约束为"思考 → 关联路径 → 最终 SQL"，配合方言规则，把生成关进"真实存在的表字段 + 目标方言"的笼子；
4. **验证与自愈**：SQLGlot AST 静态审查（强制只读、禁 DDL/DML、强制注入租户 / 时间分区隔离）→ 沙箱 Dry-Run 预演 → 报错带 Traceback 触发自动修复（限重试次数，如 2 次）。

### 安全与治理（企业必做）

- **多层物理隔离**：意图理解层 / Schema 感知层 / 沙盒执行验证层 / 结果渲染层，层间不直接暴露生产库；
- **只读副本 + 拒绝 DDL/DML**：用 `EXPLAIN` 做执行代价预演，触发全表扫描等灾难性操作时强制重置回上一稳态；
- **行列级安全（RLS / CLS）**：敏感列掩码，客服查不了薪资；高风险聚合 / 写操作执行前 **HITL 二次确权**，全链路审计；
- **成本与资源治理**：cost cap 封顶、查询超时、结果行数上限、强制分区过滤；
- **结果可解释**：指标定义来源血缘脚注，让"这个数怎么算的"可追溯。

### 评测与回归（企业级质量门禁）

- **Golden Set（黄金查询集）**：真实业务问题 + 期望 SQL，执行准确率门槛（如 ≥92%），作为发布门禁；
- **越权即事故**：`policy_violation_rate = 0`，安全违规零容忍；
- **体验指标**：首次生成正确率（first_correct_sql_rate ≥75%）、指标可溯源率 100%；
- 用真实业务问题集持续回归，防止口径 / Schema 变更悄悄引入准确率回退。

### 示例提示词（受约束生成）

```
你是一名数据查询助手。请基于【候选表字段】和【已注入的真实取值】生成一条 SQL。

约束：
1. 只能使用给定表字段，禁止编造不存在的表或字段；
2. 严格遵循给定指标口径与依赖字段，不得自行更改计算逻辑；
3. WHERE 条件中的取值必须来自给定的真实枚举值，不得凭印象编造；
4. 只读查询，禁止 INSERT / UPDATE / DELETE 等写操作；
5. 符合目标方言；聚合 / 表达式列必须用 AS 起别名；
6. 只输出 SQL 纯文本，不要 Markdown 代码块或解释。
```

## 本项目的做法（见另一个项目）

modular-rag 明示暂未实现结构化查询（边界清楚），结构化能力由独立项目 **retail-text2sql-agent** 落地。其实现路径（Agent + RAG）：

```
理解问题 → 抽取关键词 → 三路并行召回（字段·向量 / 取值·ES全文 / 指标·向量）
  → 合并补全（去重 / 补指标依赖字段 / 追加主外键 / 取值回填字段示例）
  → 双路裁剪（filter_table / filter_metric，LLM 只"选"不重建）
  → 注入时间/方言 → 生成 SQL → EXPLAIN 校验 →（失败）纠错 → 执行
```

- **关键词抽取**：`prompt | llm | JsonOutputParser` 抽出列 / 指标 / 取值三类关键词；
- **三路召回**：字段与指标用 Embedding（Qdrant）语义召回，取值用 ES + IK 分词全文召回；
- **合并补全**：指标依赖字段补齐、每张被召回的表强制附加主外键（否则 JOIN 无键可用）、取值塞进字段 examples 作生成参考；
- **LLM 裁剪**：模型只输出"选哪些表 / 字段 / 指标"，结构裁剪在程序端完成，不信任模型重建嵌套结构；
- **时间 / 方言注入**：`date.today()` 动态取当前日期，`select version()` 实时读目标库方言；
- **EXPLAIN 校验闭环**：只解析不执行，报错信息 + 完整上下文一起交给 LLM 纠错；
- **离线元数据构建**：统一 ID = `表名.字段名`，MySQL（结构）+ Qdrant（向量）+ ES（全文）三存储对齐，从数仓自动采集真实表结构与字段示例值。

### 与通用做法的差异

| 维度 | 企业级通用做法 | 本项目落地 | 差异说明 |
|------|--------------|-----------|---------|
| 指标口径 | 独立语义层 / 指标层，统一注册 + 血缘 | 指标定义与依赖字段写入元数据库，向量召回后由提示词强制遵循 | 轻量版口径治理：靠"指标-字段依赖显式建模"受控，无独立指标计算层 |
| 安全 | 行列级安全（RLS/CLS）、脱敏、HITL 审批 | 只读约束 + EXPLAIN 校验（解析不执行） | 侧重"不写不误伤"，权限管控未展开 |
| 校验 | AST 静态审查 + 沙箱 Dry-Run + 执行反馈 | EXPLAIN 语法 / 元数据校验 | 用数据库真实解析代替模型自检，安全且可信 |
| 别名映射 | 语义层 / 维护性字典 | Embedding 向量召回 + ES 全文 | 语义召回能泛化未收录别名 |
| 评测 | Golden Set + 安全门禁 + 回归集 | README 未提及评测闭环 | 可作为后续增强方向 |

## 收益与边界

- 收益：统计 / 聚合 / 排名类问题从"不可答"到"精确答"；口径受控降低"答错但看起来对"的风险；
- 边界：schema / 语义治理投入前置、权限审计成本、生成质量不稳定，需兜底（失败降级到文本检索 / 追问澄清）。

## 演进与关联

与多知识库路由（D2）、function-calling 互补；是 RAG 从"检索"走向"计算"的关键一步。
