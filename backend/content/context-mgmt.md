## 为什么需要它

上下文窗口是模型当前可见的"工作记忆"，容量有限。上下文管理在窗口内做取舍：接近上限时用分层压缩（大文件落盘 → 对话修剪 → 旧工具结果压缩 → LLM 摘要）收敛历史、保留关键信息。摘要需保留用户目标、已确认事实、失败原因等关键信息。它与记忆（跨会话）、RAG（外部知识）分工互补——会话内靠管理、跨会话靠记忆、领域知识靠检索。

## 怎么解决

难点是**压缩不丢关键信息**——粗暴清空会让 Agent 在长任务中"忘记初心"；压缩策略还要与 Prompt Cache 的前缀缓存协同，避免改动靠前内容导致缓存失效、成本上升。业界做法是**分层压缩流水线**，遵循"便宜的先跑，贵的后跑"，且**每层各管一件事、互不重叠**——同一内容只被一层处理一次，杜绝无用的重复压缩：

1. **大文件落盘（预算裁剪）**：超大单条工具输出写盘，上下文只留指针（0 成本；管"单条过大"）
2. **snip-compact（对话修剪）**：历史过长时"掐头去尾"裁掉中间旧消息（0 成本；只管"条数过多"）
3. **micro-compact（旧工具结果压缩）**：更早的超长工具结果截断保留头部，最近几条保留原文（0 成本；只管"单条偏大且旧"）
4. **auto-compact（LLM 摘要）**：万不得已时调用 LLM 全局摘要（高成本，兜底；管"仍超限"）

前三层全部本地、确定性、零 API 成本；原始历史保留以便回滚（压缩只作用于发给模型的副本，不动 checkpointer 与 Prompt Cache 前缀）。

## 核心实现

```python
# 分层压缩管线：落盘(源头) → snip → micro → auto（成本递增，触发才执行，职责互斥）
def build(messages):
    # 1) snip-compact：只管"条数"——掐头去尾 + 边界保护 + 去重/合并（不截工具内容，截断在 micro）
    if len(messages) > MAX_MESSAGES:
        msgs = drop_duplicates(messages)           # 删相邻完全重复消息
        msgs = merge_consecutive_assistant(msgs)   # 合并连续同内容无 tool_calls 的助手消息
        start = max(KEEP_HEAD, len(msgs) - KEEP_TAIL)
        while msgs[start].type == "tool":          # 边界保护：不拆散 tool_use/result 配对
            start -= 1
        result = msgs[:KEEP_HEAD] + msgs[start:]
    # 2) micro-compact：只管"旧工具结果体积"——更早的超长结果截断保留头部关键信息
    #    （截断保头部，而非清空成零信息占位符；落盘指针与短文本不动，避免重复压缩）
    # 3) auto-compact（可选）：仍超限 → LLM 结构化摘要替换旧消息

# 大文件落盘（源头）：工具输出超阈值 → 写盘 + 上下文只留指针（指针含路径，后续层不再截断/占位）
def maybe_offload(text):
    if len(text) <= THRESHOLD: return text
    write_disk(text); return "[输出已落盘] 完整内容 N 字符，已保存至 offload/xxx.txt，需要时用 run_command 读取"
```

> **不重复压缩原则**：超大单条在源头就落盘成短指针（之后受保护）；截断职责只属于 micro（snip 只做条数治理）；短文本与落盘指针 micro 一律跳过。这样一条内容最多被压缩一次，不会出现「落盘 → 截断 → 占位」叠加。

auto-compact 的示例引导语（结构化摘要，输出 goal / decided / failed / todo 四字段）：

```
你是对话摘要器。把用户提供的多轮对话压缩为结构化摘要，只保留对后续任务仍有用的信息。
严格按以下 JSON 输出，不添加原文没有的信息，每条不超过 20 字：
{
  "goal": "用户当前真实目标，一句话",
  "decided": ["已确认的事实/决策，逐条"],
  "failed": ["已尝试方案与失败原因，逐条"],
  "todo": ["未完成事项与下一步行动，逐条"]
}
```

## 本项目的做法

四层管线已落地到 runner 的 `_make_inputs`（**读时压缩**，四模式一次接入）：snip-compact / micro-compact / 大输出落盘默认开启，auto-compact 配置门控（默认关，需开启）。压缩只作用于发给模型的副本，checkpointer 原始历史保留可回滚；前端通过 `context` SSE 事件卡片可视化每层动作（对话修剪 / 工具结果占位 / 历史摘要 / 大输出落盘）。run_command 单点粗暴截断 4000 字符的缺口保留（落盘接管的是截断后文本），全文落盘接管留待后续。

**演示支持**：真实触发条件苛刻（snip 需 50+ 条消息、落盘需超大输出），为此提供两个开箱即用的演示入口——
- **「每轮压缩」模式**：前端能力选配可填「保留轮数」N（默认 3），随请求体 `context_keep_rounds` 传入。后端把保留量换算为 `keep_head(3) + N×2` 条消息，历史一旦超过保留量，**之后每轮都触发** snip 掐头去尾 + micro 截断更早工具结果，页面持续出现压缩卡片；填 0 则回退系统默认阈值。
- **大输出落盘工具**：内置 `big_output` 能力（大输出演示），固定输出 5000+ 字符，天然超默认 3000 落盘阈值 → 触发 offload，页面出现落盘卡片。可与每轮压缩模式组合演示。

> **形态定位**：本项目当前为**单机 Web 形态**（云端形态的子集）。落盘到服务端 `backend/data/offload`，但**回读闭环未打通**——指针提示「可用 run_command 读取」，而 run_command 在沙箱 work 目录执行、读不到 offload 目录；前端也只有落盘卡片、无查看/下载通道。下面给出云端与 CLI 两种形态的完整闭环设计，作为演进参照。

## 云端的做法（服务端闭环）

模型与文件系统分离，服务端是唯一可信源：一切大内容**指针化**进上下文，本体存对象存储，访问过鉴权，治理靠配额与 TTL。下面是**企业级大输出落盘的完整设计**（暂未在单机形态实现，作为演进参照）：

```
落盘: maybe_offload → 对象存储（按租户分区）→ 上下文只留指针
模型回读: read_offload(file_id) 只读工具 → 鉴权 → 取回片段（限长/分段）
用户查看: 前端卡片 → GET /api/files/download?file_id= → 下载
治理: 全局总量上限 + TTL（过期回收）+ md5 内容去重 + 租户配额
```

**① 先分级、再落盘**（不做"一刀切写盘"）。单条输出按量级走分级矩阵：

| 量级 | 处理 | 成本 | 语义 |
|---|---|---|---|
| < 1K | 原样进上下文 | 0 | 无需处理 |
| 1K–10K | 截断保头部 + 可回读 | 低 | 留摘要、丢细节 |
| 10K–1M | 落盘 + 指针 + 懒加载 | 中 | 本体离窗、按需回读 |
| > 1M | 拒绝 / 流式分块 / 降级 | 高 | 防御超大内容 |

**② 预算管理器（决策层）**——不是工具返回后被动判断，而是在产出时就评估量级给出策略：

```python
def on_tool_result(output, ctx):
    size = len(output)
    level = classify(size)                    # 分级：small / medium / large / xlarge
    if level == small:   return inline(output)                # 直接进窗口
    if level == medium:  return truncate_head(output) + link  # 保头 + 回读链接
    if level == large:   store = put_object(tenant, output)   # 对象存储，按租户分区
                         return pointer(store)                # 上下文只留指针
    if level == xlarge:  reject_or_stream(output)             # 拒绝 / 分块
```

**同步决策、异步落库**：指针立即可用，大文件本体走异步队列 + 消息，不阻塞模型链路。

**③ 指针必须可回读（三端闭环）**——单机"只留指针、没有回读通道"在企业级是半成品，指针 = 元数据 + 访问入口：

```json
pointer = {
  "file_id": "...", "tenant": "...", "size": N, "digest": "md5",
  "summary": "头部摘要", "ttl": "...",
  "read_url": "/api/files/{id}?range=0-4096"    // 鉴权 + 分段读取
}
```

- **模型回读**：只读工具，鉴权 + 限长 + 分段，模型按需取片段而非全文
- **用户回读**：前端卡片可查看 / 下载，而非"只有一行路径文本"
- **系统回读**：审计、重放、数据抽取都能定位本体

**④ 治理四闸门**（防存储爆炸）：

| 闸门 | 作用 |
|---|---|
| 全局配额 + 租户配额 | 总量上限，防单租户 / 总量失控 |
| TTL 生命周期 | 到期回收，落盘文件与会话快照**一起回收** |
| 内容级去重（md5） | 相同内容只存一份，指针复用 |
| 审计日志 | 谁落了盘、谁读了、何时回收，可追溯 |

**⑤ 与压缩链路协同**（不重复压缩）：落盘是压缩流水线的**预算层**，职责互斥——落盘后**指针受保护**，下游截断层见到指针即跳过，避免「落盘 → 截断 → 占位」叠加；回读按需取片段、不回灌本体，否则等于没压缩。

**⑥ 安全与可观测**：落盘前敏感内容扫描（正则 / 模型分类），命中则加密或拒绝；**读指针 ≠ 能读本体**，本体接口独立鉴权；指标（落盘量 / 命中率 / 回收量 / 租户分布）进监控大盘。

**历史记录闭环**：会话索引表（DB，标题/摘要由 LLM 生成）+ 消息与检查点（Postgres/Redis，大文本指针化）+ 大文件本体（对象存储）。恢复会话走 checkpoint + 指针懒加载；保留策略 TTL 让「会话快照 + 关联落盘文件」**一起回收**，防存储爆炸。

**上传文件闭环**：上传 → 校验（大小/类型/魔数）→ 对象存储 → 异步解析（沙箱内跑 OCR/PDF）→ 策略分派（小文本指针注入 / 知识类入 RAG 索引 / 脚本类落盘留沙箱处理）→ 会话内 `file://id` 引用 → 租户隔离 + TTL + 配额。

## CLI 的做法（本机文件闭环）

模型与文件系统同机，**文件即一等公民**，无需服务端中转：

**大输出落盘**：落盘到本地 `~/.my-agent/offload`，指针给绝对路径，模型用**本机只读 read 工具**直接读全文（路径白名单限 offload 根），用户用文件管理器直接打开；治理退化为单机 TTL + 总量。

**历史记录**：本地 `sessions/` 目录——`transcript.jsonl`（追加式，只追加不改写，可重放可审计）+ `checkpoint.json` + `summary.md`；目录扫描即会话列表；`--continue` / `--resume <id>` 恢复；备份 = 目录打包。

**上传文件**：没有「上传」概念——文件本就在本地磁盘，用户直接给路径，Agent 用只读工具 / 沙箱命令按需读取处理。

**形态对比**：

| 维度 | 云端 | CLI |
|---|---|---|
| 模型与文件 | 分离，指针 + 服务端中转 | 同机，文件直接可读 |
| 存储 | 对象存储 + DB（状态/索引） | 本地文件（JSONL + checkpoint） |
| 历史访问 | HTTP API + 前端 UI | 文件系统 + 终端命令 |
| 多租户 | 隔离 + 配额 + TTL + 审计 | 无 |
| 大输出回读 | `read_offload` 工具（鉴权） | 本机 read 工具（路径白名单） |
| 上传文件 | 校验 → 异步解析 → 指针/RAG | 本地路径直接引用 |

## 收益与边界

- 分层压缩替代粗暴清空：大输出落盘 + 对话修剪 + 工具占位覆盖最常见问题，LLM 摘要只做兜底
- 零成本层确定性、可回归测试；边界保护保证裁剪后工具调用配对完整
- 与记忆、RAG 明确分工：会话内 / 跨会话 / 外部知识
- 边界：auto-compact（LLM 摘要）默认关闭，需配置开启；压缩只作用于副本，长会话每轮重复执行零成本层
