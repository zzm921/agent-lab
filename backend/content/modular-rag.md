## 概述

Modular RAG（模块化 RAG）把「检索、生成、路由、记忆」等能力拆成**独立模块 + 算子（operator）**，模块可插拔、流程可组合。相比 Advanced RAG 的「整条管道」，它允许针对不同查询**按需动态编排**——是 RAG 从「固定流水线」走向「可配置系统」的一步。

## 为什么需要

Advanced RAG 的问题不是效果，而是**僵化**：

- 组件绑死在一条管道里，无法单独复用（比如换个路由策略要动整条链路）；
- 所有问题走同一套流程，无法按复杂度分级处理；
- 新能力（记忆、路由、评估）难以插进现有链路。

Modular RAG 的价值：**组件可插拔、流程可路由、能力可组合**——同一套模块，能拼出简单问题的快速链路，也能拼出复杂问题的多轮链路。

## 概念来源（LEGO-like 可重构框架）

「Modular RAG」的正式定义来自高云帆等人的同名论文（arXiv:2407.21059）——把复杂的 RAG 系统**分解为独立模块（module）+ 专用算子（operator）**，得到「类乐高」的可重构框架：

- **模块**：承担一类职责的可插拔单元（索引 / 预检索 / 检索 / 后检索 / 生成 / 路由调度），彼此有 schema 化的输入输出；
- **算子**：模块内可替换的具体实现（如「检索模块」下的向量检索 / BM25 / 图检索多个算子）；
- **路由 / 调度 / 融合**：模块化 RAG 超越传统线性架构的关键——不再是「先检索后生成」一条直线，而是由路由决定「走哪条路」，调度决定「并行还是迭代」，融合决定「多路结果怎么合并」。

关键区分：把代码拆成多个函数**不是** Modular RAG——那仍是一条流水线被切了几段。Modular RAG 的本质是控制流从**线性管道**跃迁为**模块化图（DAG）**，可分支、可循环、可并行、可替换。

## 模块与算子体系

| 模块 | 常见算子 | 作用 |
|------|---------|------|
| **索引模块** | 切分（固定/语义/父子）、元数据增强、向量化、图构建 | 建库阶段的组织能力 |
| **预检索模块** | 查询改写、HyDE、Multi-Query、意图分类 | 检索前优化 |
| **检索模块** | 向量检索、BM25、混合检索、图检索、Web 检索 | 多路召回 |
| **后检索模块** | Rerank 精排、上下文压缩、去重过滤 | 检索后优化 |
| **生成模块** | prompt 组装、引用约束、流式输出 | 最终作答 |
| **路由/调度模块** | 按复杂度路由、按数据源路由、多路并行编排 | 决定「哪条流程」执行 |
| **记忆模块** | 会话历史、检索历史复用 | 多轮与长期状态 |

## 四类流程（模块组合的方式）

| 流程类型 | 说明 | 典型场景 |
|---------|------|---------|
| **线性 Flow** | 模块依次执行，固定顺序 | 简单问答（同 Advanced） |
| **条件 Flow** | 按条件决定走哪条分支 | 意图分类：常识问题直接答 / 专业问题走检索 |
| **分支 Flow** | 多路并行执行再汇聚 | 混合检索：向量 + BM25 并行召回后融合 |
| **循环 Flow** | 模块可迭代执行 | 迭代检索：检索 → 评估 → 不足再查（Agentic 雏形） |

## 常见控制模式（算子级分类）

除了四种「流程」，业界（RAG 综述及其工程化实践）还常按**控制模式 / 算子**给 Modular RAG 归类，把这四种流程落到更细的通用原语上：

| 控制模式 | 做什么 | 对应流程 |
|---------|--------|---------|
| **Router（路由）** | 按查询类型/数据源选路 | 条件 Flow |
| **Multi-Retriever（多检索器）** | 多种检索器并行召回再融合 | 分支 Flow |
| **Branch（分支）** | 同一查询拆多路并行 | 分支 Flow |
| **Iterative（迭代检索）** | 检索 → 生成 → 不足再查 | 循环 Flow |
| **Recursive（递归检索）** | 为处理当前查询而递归发出子查询 | 循环 Flow |
| **Adaptive（自适应）** | 按查询复杂度动态选择策略 | 条件 Flow 的进阶 |
| **Fusion（融合）** | 多路结果 RRF / 加权 / 重排融合 | 分支 Flow 的汇聚 |

其中 **Adaptive / Router** 是 Modular RAG 最具代表性的形态：用分类器或规则在检索前判断「这个查询到底需要哪种策略」，把「固定管道」变成「按需编排」。

## 路由与调度（Adaptive RAG 思路）

Modular RAG 的进阶形态是**自适应路由**：用一个小模型或规则先判断查询复杂度，再动态选择流程——

- **简单问题** → 直接生成，不检索（省延迟）；
- **单点事实** → 单次检索 + 生成；
- **复杂问题** → 多轮迭代检索，甚至升级到 Agent 决策。

这即 **Adaptive RAG**：把「按查询复杂度动态选策略」落到模块化框架里，是 Modular 走向 Agentic 的桥梁。原始实现中，复杂度判定由一个**专门的分类器（通常是小模型）**完成——从「不检索 / 单步检索 / 迭代检索」三档中动态选最合适的一档；工程上也可退化为**规则 / 轻量提示词**判断，避免每次检索前都调用一次大模型。

## 不同分支（控制流执行路径）

Modular RAG 的「按需编排」最终落到**一条条可复用的分支**上。本项目里，路由决策经调度层映射为执行计划，再按计划动态挂载/跳过模块——不同复杂度的查询走不同分支，每条分支由一组示例 Prompt 驱动（完整示例见下方「推荐 Prompt（按分支）」）：

| 分支 | 路由判定 | 执行计划（模块链） | 典型问题 | 前端检索事件 |
|------|---------|-------------------|---------|-------------|
| **不检索** | `retrieval_need=false` | 无模块，直接生成 | 你好 / 今天几号 | `classify` → 直接作答 |
| **单次检索** | `complexity=simple` + `vector` | `search` | 口语化单点事实 | `classify` → `retrieve` |
| **单次混合** | `complexity=simple` + `hybrid` | `hybrid_search` | 含领域词/编号/数字 | `classify` → `retrieve` |
| **改写** | `complexity=rewrite` | `rewrite` → `multi_recall`/`hybrid_search` → `rerank` → `compress` | 含指代/省略（如「那补卡流程呢」） | `classify` → `rewrite` → `retrieve` →（`compress`） |
| **分解** | `complexity=decompose` | `decompose` → `multi_recall` → `rerank` → `compress` | 对比/多实体（如「出差和报销有什么区别」） | `classify` → `decompose` → `retrieve` →（`compress`） |
| **多跳** | `complexity=multihop` | `multi_hop`（规划-执行-验证）→ `rerank` | 实体链/流程（如「张三的领导有几天年假」） | `classify` → `multi_hop_plan` → 逐跳 `multi_hop` → `multi_hop_verify` → `retrieve` |

几个关键设计点：

- **分支可跳过**：简单问题只挂最少模块（单次检索连改写/重排都不上），复杂问题才挂全链路——这正是「模块可插拔、可跳过」的具象，也是 Modular 相对 Advanced「一刀切跑全链路」的成本优势。
- **充分性闸门跨分支兜底**：无论走哪条分支，检索完成后都统一过「答案充分性验证」——`answerable` 直接生成；`escalate` 有界升级 1 轮（单次/混合 → 多路召回 → 多跳）；`clarify` 如实上报缺口并追问澄清（不编造）。升级路径也体现为「换一条更全的分支重跑」。
- **路由判定是纯 LLM**：单跳/多跳这类语义判定交给模型（输出决策 JSON、枚举白名单校验），**不做规则正则兜底**——避免把「张三的领导是谁」这类只问关系实体的单跳事实题误判为多跳；未配置聊天 Key 或路由调用失败时直接报错提示。

## 推荐 Prompt（按分支）

每条分支都由一组**示例 System Prompt** 驱动（按此思路可复用到任意 RAG 实现）。通用约定：结构化 JSON 输出 + 枚举白名单校验（非法即报错或回退规则实现）；LLM 场景与模型参数见 LLM 服务配置的 `DEFAULT_PROFILES`。

### 1. 语义路由分支（路由判定）

**作用**：检索前输出五维结构化路由决策（D1 检索必要性 / D3 检索策略 / D4 复杂度 / D5 生成模式 + 置信度/理由），驱动执行计划编排。**纯 LLM、无规则兜底**。

**模型参数**：`qwen3.5-flash / temperature=0.2 / max_tokens=500 / enable_thinking=False`

**示例 Prompt**：

```
你是 RAG 系统的语义路由引擎（Query Router）。你的唯一职责是分析用户输入，
输出一条检索路由决策 JSON。你不是问答助手，不回答用户问题。

本系统面向企业考勤、差旅、报销、人事制度问答，知识库为此领域语料。

字段语义（枚举值必须从下列值中选择，禁止自造）：
- retrieval_need（bool）：是否检索。寒暄/常识/通用推理 → false；事实性/领域性/需引用来源 → true。
- retrieval_mode（str）：vector=纯语义（口语化/概念性）；hybrid=混合检索（含领域词/编号/数字时优先）；
  multi_recall=多路召回（多实体/对比/多条件）。
- complexity（str）：simple=单跳直接检索；rewrite=含指代/省略，需先改写；
  decompose=对比/多实体/多条件，需拆分子查询；
  multihop=多跳/流程/原因链/实体链（查某人领导的属性，如「张三的领导有几天年假」；
  仅问「领导是谁」不算，属 simple 单跳），需迭代检索多轮。
- generation_mode（str）：direct=直接回答不引用来源；citation=引用来源回答（默认）；comparison=结构化对比输出。
- confidence（float 0~1）：本次判断的把握程度。
- reason（str）：一句话说明分类依据。

常见组合（尽量遵循，与后续编排一致）：
- 寒暄/常识 → retrieval_need=false + vector/simple/direct；
- 单点事实 → simple + vector 或 hybrid + citation；
- 只问「X的{关系}是谁/叫什么」（如「张三的领导是谁」）→ simple 单跳直接检索（关系实体本身不是多跳）；
- 含指代/省略 → rewrite + hybrid 或 multi_recall + citation；
- 多跳/流程 → multihop + multi_recall + citation；
- 对比/多实体 → decompose + multi_recall + comparison。

输出必须严格是以下 JSON（不要输出任何其他文字）：
{"retrieval_need": true/false, "retrieval_mode": "vector|hybrid|multi_recall",
 "complexity": "simple|rewrite|decompose|multihop",
 "generation_mode": "direct|citation|comparison",
 "confidence": 0.0~1.0, "reason": "一句话"}

当 retrieval_need=false 时，retrieval_mode/complexity/generation_mode 统一填 vector/simple/direct。
（随后跟 6 组 few-shot：单点事实 / 单跳关系 / 对比 / 指代 / 多跳 / 寒暄）
```

**输出校验**：提取 `{...}` JSON → 三枚举白名单校验（非法抛错）→ 置信度归一化。

### 2. 改写分支（两个 Prompt）

**作用**：把口语化/含指代的问题改写成可独立检索的查询——查询改写（Multi-Query）生成多个变体补召回，指代消解把「他/那…」替换为具体实体。

**模型参数**：`qwen3.5-flash / temperature=0.3 / max_tokens=200 / enable_thinking=False`

**① 查询改写（示例 Prompt）**：

```
你是企业知识库检索助手。请把用户的问题改写成 3 个
更适合检索企业制度语料的查询变体：保留关键实体与数字，
用更正式、贴近规章制度原文的措辞；若原问题已足够正式，可做关键词化压缩。
每个变体单独一行输出，不要编号、不要解释、不要其他文字。
```

**② 指代消解（示例 Prompt）**：

```
你是企业知识库检索系统的指代消解器。用户当前问题可能含指代词
（他/她/它/这个/那个/该…），需要根据下方对话上下文把它替换为具体实体，
输出一条**不含指代词、可独立检索**的查询。
规则：
- 指代对象**优先取上一轮助手回答中「给出/确定」的实体**
  （即上轮用户问题的答案对象），而不是上轮用户问题的主语。
  例如：用户问「张三的领导是谁」、助手答「是王刚」时，
  后续「他的年假有多少天」中的「他」指王刚，应改写为「王刚的年假有多少天」；
- 上下文不足以确定指代对象，或问题本来就没有指代 → 原样输出当前问题；
- 只输出一条查询，不要解释、不要其他文字。

对话上下文：
{最近会话上下文}
```

### 3. 分解分支

**作用**：对比/多实体问题（如「出差和报销有什么区别」）拆成可独立检索的子问题，分别召回后融合。

**模型参数**：`qwen3.5-flash / temperature=0.3 / max_tokens=300 / enable_thinking=False`

**示例 Prompt**：

```
你是检索系统的查询分解器。请把用户的复杂问题拆分为若干个
可以独立在知识库中检索到答案的简单子问题。要求：
1. 每个子问题可独立检索；
2. 子问题之间尽量无重叠；
3. 所有子问题答案合并后可回答原始问题。
每个子问题单独一行输出，不要编号、不要解释、不要其他文字。
```

### 4. 多跳分支（规划-执行-验证，三个 Prompt）

**作用**：`complexity=multihop` 的实体链/流程问题（如「张三的领导有几天年假」）走规划 → 逐跳执行 → 验证对表。

| 阶段 | 调用类型 | 模型参数 |
|------|---------|---------|
| 规划 | 轻量决策（关闭思考，加速规划） | `qwen3.5-flash / temp=0.2 / max_tokens=300 / thinking=False` |
| 验证 / 逐跳覆盖 | 轻量决策（关闭思考） | `qwen3.5-flash / temp=0.2 / max_tokens=400 / thinking=False` |
| 下一跳决策 | 轻量决策（关闭思考） | `qwen3.5-flash / temp=0.3 / max_tokens=300 / thinking=False` |

**① 规划（示例 Prompt）**：

```
你是多跳检索的「子查询规划器」。给定原始问题，一次性输出一份子查询执行计划：
1. 把多跳问题按依赖关系拆成若干子查询（如「张三的领导有几天年假」：
  先查「张三的领导是谁」、再查「王刚的年假有多少天」）；
2. 每步包含：
   - target：本步要解决的"目标维度/事实"（一句话，如"领导是谁"/"年假天数"）；
   - query：可独立检索的子查询；
   - entity：若本步可预判其关键实体/概念，填该实体（如第2步可预判为"王刚"）；否则填 null；
   - depends_on：本步依赖的先前 target 列表（无则 []）；
3. 子查询之间尽量无重叠；若已是单跳事实题，输出 1 个步骤即可。
输出必须严格是以下 JSON（不要输出任何其他文字）：
{"steps": [{"target": "...", "query": "...", "entity": "..."|null,
 "depends_on": ["..."]}], "reason": "一句话说明规划思路"}
```

**② 验证 / 覆盖对表（示例 Prompt）**：

```
你是多跳检索的「质量验证器」。给定原始问题、子查询计划（含目标）
与已累计检索到的内容，判断：
1. 对计划中的每个 target，判断其要解决的事实/环节是否已被已检索内容覆盖
  （该事实或等价信息是否已出现）；
2. covered：已覆盖的 target 列表；missing：未覆盖的 target 列表；
3. 对每个 missing target，若仍有可能检索到，生成一个聚焦该缺口的、
  可独立检索的补缺子查询 patched（每项 {target, query}）；
4. 若已检索内容足以覆盖全部 target，patched 输出 []。
输出必须严格是以下 JSON（不要输出任何其他文字）：
{"covered": ["..."], "missing": ["..."],
 "patched": [{"target": "...", "query": "..."}]}
```

**③ 下一跳决策（示例 Prompt）**：

```
你是多跳检索的「下一跳查询生成器」。给定原始问题与目前已累计检索到的全部内容，判断：
1. 先基于已检索内容解析原始问题中已知的环节（例如已检索到「张三的领导是王刚」，
  则「张三的领导是谁」这一环已解决，不应再查）；
2. 若已检索内容足以回答原始问题 → 输出 {"continue": false}；
3. 若仍缺关键信息（中间环节、前置条件、后续步骤、原因链的下一环），且该信息未出现在
  已检索内容中 → 输出 {"continue": true, "next_query": "聚焦缺失环节、可独立检索的子问题"}；
4. 下一跳查询应直接使用已解析出的实体与结论推进（如已得出「领导是王刚」，下一跳应为
  「王刚的年假有多少天」，而不是「张三的领导是谁」）；
5. 不得重复查询已检索内容中已出现的信息。
输出必须严格是 JSON，不要输出任何其他文字。
```

### 5. 充分性闸门（跨分支兜底）

**作用**：所有分支检索（含后处理）完成后、生成之前判断「当前上下文是否足以回答」——`answerable` 直接作答 / `escalate` 有界升级 1 轮（单次/混合 → 多路召回 → 多跳）/ `clarify` 如实说明缺口并追问澄清（不编造）。

**模型参数**：复用验证场景（`qwen3.5-flash / temp=0.2 / max_tokens=400 / thinking=False`）

**示例 Prompt**：

```
你是 RAG 系统的「答案充分性验证器」。给定用户问题与检索到的知识库内容，
判断当前内容是否足以支撑回答该问题。你不是问答助手，不回答用户问题。
判定规则：
1. answerable（bool）：检索内容是否足以支撑回答用户问题；
2. missing_facts（list）：若不足以回答，列出缺失的关键事实/信息
  （如「王刚的在岗工龄」「具体报销时限」）；足以回答则为 []；
3. recommendation（str）：answer=足以回答直接作答；
  escalate=该关键事实很可能在知识库中、只是本次未检索到
  （扩大召回/换更全的检索方式有机会命中），建议升级检索；
  clarify=知识库明显缺乏该关键事实（需用户补充信息），建议追问澄清，
  不要依赖自身知识编造内部人事数据；
4. escalate_to（str，仅 recommendation=escalate 时）：
  "multi_recall"=升级为多路召回（双路宽召回，针对漏召回）；
  "multihop"=升级为多跳检索（缺失的是实体链/流程中间环节）。默认 "multi_recall"。
输出必须严格是以下 JSON（不要输出任何其他文字）：
{"answerable": true/false, "missing_facts": ["..."],
 "recommendation": "answer|escalate|clarify",
 "escalate_to": "multi_recall|multihop"}
```

### 6. 生成作答（注入式，全分支共用）

RAG 的最终回答**不额外调用「RAG 生成模型」**，而是把检索命中注入主对话的用户消息（注入式增强）——保证所有推理模式（react / plan_execute / reflection / multi_agent）首次模型调用都能看到上下文。推荐注入模板：

```
{用户原始问题}

【知识库检索结果（{方案名}）】
[相关度 0.91] {命中片段1}
[相关度 0.87] {命中片段2}
...

{指令}
```

- 检索充分时：`请优先基于以上检索内容回答；若内容不足以回答，再结合自身知识补充。`
- 充分性闸门判「不足」时：`请严格基于以上检索内容如实回答；若检索内容不足以回答用户问题，请明确说明缺失的关键信息，并礼貌地向用户追问补充，不要编造、不要依赖自身知识臆测内部人事数据。`

## 收益与边界

**收益**

- 灵活可复用：模块独立演进、跨项目复用；
- 按需组合：同一套模块拼出不同复杂度链路，成本可控；
- 易扩展：新能力（记忆、评估、新检索源）即插即用。

**边界 / 局限**

- 工程复杂度高：模块拆分、流程编排、路由策略都需要设计与调优投入；
- 仍是「先检索后生成」范式：路由只是选路径，不改变底层「文本匹配」的检索本质；
- 需要评估闭环支撑：模块多了，哪一环掉链子需要独立度量才能定位。

## 本项目的做法

本项目把 Modular RAG 落地为多方案框架中的 **modular** 方案（与 naive / advanced 并列，侧边栏可切换）：核心新增**前置语义路由（Query Router）→ 执行计划（Execution Plan）→ 动态编排模块执行**，检索算子**直接复用 advanced 已实现的模块**（改写 / 混合检索 / 重排等），并新增查询分解、上下文压缩、多跳规划-执行-验证等模块——这正是「模块可插拔、能力可复用」的具象。

- **结构化路由决策**：检索前调用路由器，输出一份决策 JSON——对齐企业级「五维决策」（D1 检索必要性 / D2 知识库路由 / D3 检索策略 / D4 查询复杂度 / D5 生成模式），因本项目为**单知识库**省略 D2 知识库路由维度，实际落地其余四维 + 置信度/理由：
  - D1 `retrieval_need`：要不要检索（寒暄/元问题 → 短路直接生成，省延迟）；
  - D3 `retrieval_mode`：检索策略（`vector` 向量 / `hybrid` 混合 / `multi_recall` 多路召回）；
  - D4 `complexity`：查询复杂度（`simple` 单次 / `rewrite` 改写后检索 / `decompose` 分解后检索 / `multihop` 多跳迭代检索）；
  - D5 `generation_mode`：生成模式（`direct` 直接回答 / `citation` 引用回答 / `comparison` 对比回答）；
  - `confidence` + `reason`：置信度与判定理由，全链路可观测、可回溯。
- **执行计划**：把路由决策映射为**可组合、可跳过的模块调用链**——预处理（改写/分解）→ 检索（向量/混合/多路召回/多跳）→ 后处理（重排/压缩），生成策略随决策切换。简单问题只挂最少的模块，复杂问题才上全链路；多跳路径的「覆盖复用跳过」即体现为模块可跳过。
- **查询分解（Query Decomposition）**：对比/多实体问题（如「出差和报销有什么区别」）先拆成可独立检索的子查询，分别召回后融合，再走重排 + 压缩，解决单跳检索无法回答多步推理的问题。
- **上下文压缩（Context Compression）**：多路召回必然带来重复与噪声，进入 LLM 前做去重 + Top-K 截断 + 超长块句边界截断，控制上下文噪声、节省 token；压缩仅在实际发生（去重/截断）时向前端上报统计。
- **多跳检索（Multi-Hop，规划-执行-验证）**：`complexity=multihop` 的多跳/流程/原因链/实体链问题（如「张三的领导有几天年假」「报销发票的流程」）走专门的多跳模块，按企业级「先规划后执行、执行后验证」编排——
  - **规划（规划器）**：一次拆出子查询计划，每步含 `target`（要解决的目标维度）、可独立检索的 `query`、可预判的 `entity` 与 `depends_on` 依赖；有 LLM 时输出结构化计划 JSON，无 LLM 回退规则（实体链拆「先定位中间实体、再查其属性」两跳）；
  - **执行（覆盖检测 + 逐跳检索）**：按计划逐跳双路召回；每跳执行前复用验证器判断「累积证据是否已覆盖该步目标」——已覆盖 → **复用跳过**（`skipped`，不重查），否则照常检索，把「不重复查已解决事实」从模型自觉升级为语义闸门；
  - **验证（质量闸门）**：执行完对表计划目标——`covered` 已覆盖 / `missing` 缺口；缺口在预算内生成 `patched` 补缺子查询局部修正（而非整盘重来），最多一轮补修后二次对表，超预算则如实上报缺口（可观测）；
  - **链式证据保留**：多跳证据跨多步成链，最终保留数按**实际检索跳数**放大（`keep = top_k × 实际跳数`，覆盖复用跳不计入），避免只留单步 top_k 导致链式上下文缺失；
  - 规划 / 验证 / 覆盖判断均有 LLM 与无 LLM 规则回退双实现：规划为**轻量决策、关闭思考模式**（结构化 JSON 输出不需要推理链，关闭思考显著降低规划延迟）；验证与逐跳覆盖判断同样**轻量决策、关闭思考模式**，避免决策型调用拖慢多跳链路。
- **双实现边界**：**语义路由为纯 LLM**——单跳/多跳这类语义判定交给模型判断（输出决策 JSON、枚举白名单校验），**不做规则正则兜底**（避免把「张三的领导是谁」这类只问关系实体的单跳事实题误判为多跳）；未配置聊天 Key 或路由调用失败时直接报错提示。**查询分解 / 改写 / 多跳规划 / 验证**仍保留无 LLM 规则兜底（离线/仅配 Embedding 时降级运行）。
- **路由开关随方案配置**：路由能力内置于 modular 方案内部，`rag_schemes` 配置里含 `"modular"` 时方案被构建、路由即启用；不含则路由能力整体关闭——即「根据是否配置 modular-rag 决定是否打开前置语义路由」。
- **检索事件**：检索事件串为 `classify`（路由决策）→（按需）`rewrite` / `decompose` → `multi_hop_plan` → 逐跳 `multi_hop`（index 递增，覆盖复用带 `skipped` 标记）→ `multi_hop_verify` → `retrieve` →（按需）`compress`，前端检索卡片依次展示「语义路由 → Query 重写 / Query 分解 → 多跳规划 → 逐跳检索 → 多跳验证 → 知识库检索 → 上下文压缩」，直观看到 Modular 相对 Advanced 的「先路由、再按执行计划编排」差异。

> modular 与 advanced 的最大不同不是检索手段，而是**控制流**：advanced 对每个问题都跑固定全链路，modular 先做结构化路由决策、生成执行计划，再按计划动态组合/跳过模块——简单问题不再为「重写 + 多路召回 + 重排」浪费延迟，复杂问题也不再「一刀切」处理不足。

**暂未实现的能力（明示边界，不越权宣称）**

- **多知识库路由（D2）暂不实现**：当前为**单知识库**（云帆制度语料），语义路由只落地 D1/D3/D4/D5 四维 + 置信度/理由，不做「按知识库/数据源选择检索库」的 D2 数据源路由；
- **结构化查询（Text-to-SQL）暂不实现**：检索本质仍是「文本语义匹配」，不做「查数据库/表格结构」的结构化查询——涉及统计、排名、跨表聚合类问题（如「上月报销总额」「各部门人数排名」）不在本方案检索能力内，建议走 Agent 工具或人工核对。

上述两项在更完整的工程落地中才需要引入（多知识库路由需要多个独立库 + 数据源索引；Text-to-SQL 需要库表 Schema 与权限管控），本项目暂不实现。

## 演进方向

- **需要结构化关系** → 把「图」作为一类索引模块接入（[graph-rag.md](graph-rag.md)）；
- **需要自主决策、迭代收敛** → 让 Agent 接管路由与流程编排（[agentic-rag.md](agentic-rag.md)）。
