## 概述

Modular RAG（模块化 RAG）把「检索、生成、路由、记忆」等能力拆成**独立模块 + 算子（operator）**，模块可插拔、流程可组合。相比 Advanced RAG 的「整条管道」，它允许针对不同查询**按需动态编排**——是 RAG 从「固定流水线」走向「可配置系统」的一步。

## 为什么需要

Advanced RAG 的问题不是效果，而是**僵化**：

- 组件绑死在一条管道里，无法单独复用（比如换个路由策略要动整条链路）；
- 所有问题走同一套流程，无法按复杂度分级处理；
- 新能力（记忆、路由、评估）难以插进现有链路。

Modular RAG 的价值：**组件可插拔、流程可路由、能力可组合**——同一套模块，能拼出简单问题的快速链路，也能拼出复杂问题的多轮链路。

## 模块与算子体系

| 模块 | 常见算子 | 作用 |
|------|---------|------|
| **索引模块** | 切分（固定/语义/父子）、元数据增强、向量化、图构建 | 建库阶段的组织能力 |
| **预检索模块** | 查询改写、HyDE、Multi-Query、意图分类 | 检索前优化 |
| **检索模块** | 向量检索、BM25、混合检索、图检索、Web 检索 | 多路召回 |
| **后检索模块** | Rerank 精排、上下文压缩、去重过滤 | 检索后优化 |
| **生成模块** | prompt 组装、引用约束、流式输出 | 最终作答 |
| **路由/调度模块** | 按复杂度路由、按数据源路由、多路并行编排 | 决定「哪条流程」执行 |
| **记忆模块** | 会话历史、检索历史复用 | 多轮与长期状态 |

## 四类流程（模块组合的方式）

| 流程类型 | 说明 | 典型场景 |
|---------|------|---------|
| **线性 Flow** | 模块依次执行，固定顺序 | 简单问答（同 Advanced） |
| **条件 Flow** | 按条件决定走哪条分支 | 意图分类：常识问题直接答 / 专业问题走检索 |
| **分支 Flow** | 多路并行执行再汇聚 | 混合检索：向量 + BM25 并行召回后融合 |
| **循环 Flow** | 模块可迭代执行 | 迭代检索：检索 → 评估 → 不足再查（Agentic 雏形） |

## 路由与调度（Adaptive RAG 思路）

Modular RAG 的进阶形态是**自适应路由**：用一个小模型或规则先判断查询复杂度，再动态选择流程——

- **简单问题** → 直接生成，不检索（省延迟）；
- **单点事实** → 单次检索 + 生成；
- **复杂问题** → 多轮迭代检索，甚至升级到 Agent 决策。

这即 **Adaptive RAG**：把「按查询复杂度动态选策略」落到模块化框架里，是 Modular 走向 Agentic 的桥梁。

## 收益与边界

**收益**

- 灵活可复用：模块独立演进、跨项目复用；
- 按需组合：同一套模块拼出不同复杂度链路，成本可控；
- 易扩展：新能力（记忆、评估、新检索源）即插即用。

**边界 / 局限**

- 工程复杂度高：模块拆分、流程编排、路由策略都需要设计与调优投入；
- 仍是「先检索后生成」范式：路由只是选路径，不改变底层「文本匹配」的检索本质；
- 需要评估闭环支撑：模块多了，哪一环掉链子需要独立度量才能定位。

## 演进方向

- **需要结构化关系** → 把「图」作为一类索引模块接入（[graph-rag.md](graph-rag.md)）；
- **需要自主决策、迭代收敛** → 让 Agent 接管路由与流程编排（[agentic-rag.md](agentic-rag.md)）。
