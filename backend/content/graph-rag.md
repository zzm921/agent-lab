## 为什么需要它

向量检索擅长"一对一的局部片段匹配"，却看不懂跨文档的宏观结构与实体间关系。Graph RAG（微软 2024）把文档提炼成实体-关系知识图谱，支持多跳推理（"A 产品的供应商的 CEO 是谁"）与全局性问题（"这些文档的主要主题是什么"）。实践项目《红楼梦》知识图谱 RAG 就是典型落地形态——问「贾宝玉和林黛玉是什么关系」，纯向量只能召回"长得像"的片段，答不出藏在关系里的答案。

## 怎么解决

难点在知识图谱构建成本——从文档抽取实体关系需要大量 LLM 调用，且实体命名不统一、LLM 易臆造端点，直接进图会污染图结构。业界以 LightRAG / KAG 等轻量图方案降低预处理成本；微软原版还预构建社区摘要支持全局问答（Local Search 实体遍历 / Global Search 社区摘要 Map-Reduce）。本实践项目的做法是 **规则兜底 + LLM 抽取 + 别名归一 + 端点剪枝** 四步组合控本控质，检索端用 **图 / 向量 / 关键词三路召回 + RRF 融合**，既懂语义又懂关系，回答还逐条带《回目》出处。

## 核心实现

> **知识卡片：双存储架构**
> | 存储 | 职责 |
> | ---- | ---- |
> | Neo4j 知识图谱 | 存「关系」：Document（每回一个）/ People / Location / Event 节点 + MENTIONS / RELATED_TO / LIVES_IN / VISITED / INVOLVES / OCCURS_IN 边 |
> | Qdrant 向量库 | 存「语义」：chunk 文本向量（documents 集合，1024 维 Cosine） |
> 关键设计：每回一个「文档」节点，抽取出的实体用 MENTIONS 边挂在回上；chunk 只作为检索与向量单元、不进图——图结构干净，证据又能精确溯源到第几回。

**建库（离线）**：线性流水线，抽取与建图逐块交错进行。

```pseudocode
文档 → 按回目标题切章 → 章内按句子边界切块（1000 字/块，80 字重叠，带回目前缀）
     → 逐块抽取：规则兜底(种子词典命中) → LLM 抽取(严格 JSON) → 别名归一(凤姐→王熙凤)
              → 端点剪枝(两端必须在"本块抽取 ∪ 种子词典"内，否则丢弃)
     → 建图：节点/边按 id MERGE（幂等，重复抽取只合并不重复）
     → 向量化：Embedding → Qdrant，写入前先拉已有 ID（断点续传），10 条/批
```

**问答（在线）**：

```pseudocode
用户问题 → 查询理解（LLM 抽取实体提及 + 规则兜底，判定意图：实体/关系/比较/多跳/语义/通用）
        → 实体链接（提及 → 图节点：名称匹配 → LLM 补提）
        → 三路召回并行：
            图检索（按意图选策略：邻域展开 1~2 跳 / 比较走共享邻居 / 多锚点走路径检索
                    / 多跳做受控迭代展开，排除 hub 节点防扇出爆炸）
          | 向量检索（Embedding 语义召回）
          | 关键词检索（字面命中兜底）
        → RRF 融合 → 可选 LLM 重排（失败自动回退）→ 去重截断
        → 上下文组装（图谱上下文 + 文本片段，带《回目》前缀）
        → 生成回答（每条论断带《回目》引用，上下文不足明说"未检索到相关信息"）
```

> **知识卡片：RRF 融合**
> 三路召回各按权重排序，第 `rank` 位的证据得 `1/(60+rank)` 分，逐通道累加后统一排序。相比「图永远压过向量」的硬排序，RRF 让每个通道的高排名证据都有机会进最终上下文；同一证据多路同时命中时分数自然更高。

## 推荐 Prompt

Graph RAG 有两处需要 LLM 参与：**离线建图**（文档 → 实体/关系抽取）与**在线查询理解**（抽取提及 + 判定意图，决定走哪条检索策略）。

### 1. 实体 / 关系抽取（离线建图）

**作用**：把文档 chunk 抽成「实体-关系」结构化数据并归一化实体名，作为图谱构建的输入。Graph RAG 预处理成本高，正是因为这步要对全部文档逐个 LLM 调用——实践项目用「规则兜底先命中已知实体、LLM 只做增量发现」来压成本。

**示例 Prompt**：

```
你是《红楼梦》前二十回的实体关系抽取器。给定一个小说片段，抽取其中出现的实体与关系，只输出严格 JSON：
{
  "people": ["人物规范全名，如贾宝玉"],
  "locations": ["出现的地点，如荣国府、潇湘馆"],
  "events": ["片段中发生或明确提及的事件，如黛玉进贾府、元妃省亲"],
  "relations": [{"subject": "人物A", "relation": "父子/主仆/表亲…", "object": "人物B"}],
  "residence": [{"person": "人物", "location": "地点"}],
  "visits": [{"person": "人物", "location": "地点"}],
  "event_involves": [{"event": "事件名", "people": ["人物"]}],
  "event_locations": [{"event": "事件名", "location": "地点"}]
}
要求：只抽取片段中明确出现的，不得臆造；人物一律用规范全名（凤姐→王熙凤，宝玉→贾宝玉）。
```

### 2. 查询理解 / 检索策略路由（在线）

**作用**：从问题中抽取实体提及（人物/地点/事件/文档），并判定意图——实体问题走邻域展开、比较问题走共享邻居、多跳问题走受控迭代展开、语义问题主走向量路。图检索按意图选策略，避免无差别扇出爆炸。

**示例 Prompt**：

```
你是知识图谱检索的查询理解器。从给定问题中抽取实体提及并判定意图，输出 JSON。
- entities：问题中出现的人物/地点/事件/文档提及；
- intent：实体（指向具体实体/事实）| 关系（两个实体间关系）| 比较（多个实体共同点）
        | 多跳（经过中间实体的链式推理）| 语义（面向全文的语义查找）| 通用（其他）。
输出必须严格是以下 JSON（不要输出任何其他文字）：
{"entities": [...], "intent": "...", "reason": "一句话说明判定依据"}
```

## 收益与边界

- 实体-关系建模，弥补向量相似度的"关系盲区"
- 多跳推理：A 的供应商的 CEO 是谁 / 贾宝玉和林黛玉是什么关系
- 三路召回 + RRF 融合：语义、关系、字面互相兜底
- 可溯源：每条论断带《回目》引用
- 成本治理：规则兜底减少 LLM 调用、端点剪枝防臆造入图

**边界**：建图成本仍高于纯向量（每块一次 LLM 抽取）；新语料需重建种子词典与图谱；图规模增长后多跳检索要防扇出爆炸（实践项目用排除 hub 节点 + 1~3 跳限深控制）。

## 本项目的做法

本项目以《红楼梦》前二十回为语料，走完 **切块 → 实体抽取 → 建图 + 向量化 → 检索 → 可溯源问答** 的完整 Graph RAG 链路：Neo4j 存「关系」、Qdrant 存「语义」；实体抽取用规则兜底 + LLM + 别名归一 + 端点剪枝四步组合；问答走图 / 向量 / 关键词三路召回 + RRF 融合 + 可选 LLM 重排，回答逐条带《回目》出处。项目地址：[doc-graph-rag（红楼梦文档知识图谱 RAG）](https://github.com/zzm921/doc-graph-rag)。
